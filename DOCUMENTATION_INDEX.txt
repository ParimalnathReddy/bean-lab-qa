1. WHAT THIS PROJECT DOES (PLAIN ENGLISH)
================================================================================

The Bean Lab has over 1,000 peer-reviewed scientific papers about bean and
legume crop science — covering diseases, drought, nitrogen fixation, breeding,
agronomic management, and more. These papers span 65 years (1961–2026).

Before this system, a researcher wanting to find a fact (e.g. "what nitrogen
fixation rates have been measured for common bean?") had to manually search
PDFs. This is slow and misses connections across papers.

This project builds a web application where a researcher types a question in
plain English and gets a detailed, cited answer drawn from the actual papers
within a few seconds — completely free to use.

The core technology is RAG (Retrieval-Augmented Generation). Instead of asking
an AI to answer from memory (which hallucinations), the system:
  1. Converts all paper text into a searchable vector database
  2. When a question arrives, searches that database for the most relevant
     paragraphs across all papers (now hybrid: dense + keyword search, STEP 12)
  3. Shows those paragraphs to an LLM and asks it to synthesise an answer
     from only the retrieved evidence — citing exact DOIs
  4. Checks the answer for unsupported claims (STEP 13) and fabricated gene
     names (STEP 15) before showing it to the user

As of Changes 1-7, the system also:
  - Pulls exact numbers from a structured trial-data database when a question
    asks about a specific cultivar/location/year, instead of only hoping a
    paper chunk mentions them (STEP 16)
  - Decides which of these extra subsystems to activate per question via a
    lightweight rule-based router, not a single LLM classifier call (STEP 17)
  - Is evaluated with LLM-judged RAGAS metrics (faithfulness, answer
    relevancy, context precision/recall) in addition to keyword-rubric
    scoring (STEP 14)

This means the AI cannot make things up undetected: every claim in its answer
must come from text that is physically present in the retrieved paragraphs,
and the system now actively checks for the cases where that still goes wrong.

================================================================================

OFFLINE (runs once on HPCC, mostly GPU, some CPU-only):
  PDF files  →  [pdf_processor.py]  →  processed_chunks.json
                                             ↓
                                  [generate_embeddings.py]  (GPU, BAAI/bge-large-en-v1.5)
                                             ↓
                                       embeddings.npy (1024-dim)
                                       embeddings_metadata.json
                                             ↓
                                  [build_vector_store.py]
                                             ↓
                        ┌────────────────────┼────────────────────┐
                        ↓                    ↓                    ↓
                  vector_db/            vector_db/           (separately:)
                  chroma.sqlite3        bm25_index.pkl       [build_gene_index.py]
                  (ChromaDB, ~1 GB)     (RRF hybrid,          → vector_db/gene_index.pkl
                                         Change 2)              (NCBI Gene + UniProt,
                                                                 taxid 3885)
                                                              [extract_structured_data.py]
                                                              → vector_db/trial_data.db
                                                                (LLM-extracted trial data,
                                                                 Change 6)

ONLINE (runs on HuggingFace Spaces, free, 24/7):
  User question
       ↓
  [app.py startup: snapshot_download entire vector_db/ from HF Dataset repo —
   chroma.sqlite3, bm25_index.pkl, gene_index.pkl, trial_data.db all come for
   free through the same download, no extra app.py logic needed]
       ↓
  [query_router.route(question)]  ← rule-based, no LLM call (STEP 17)
   sets three independent flags: use_literature (~always True),
   use_structured_data, run_gene_validation — plus the actual matched
   cultivar/location/year/trait/gene entities, not just booleans
       ↓
       ├─────────────────────────────┬─────────────────────────────┐
       ↓ (parallel, ThreadPoolExecutor)                             ↓
  [BeanRetriever.retrieve()]                              [structured_data.query_trial_data()]
   expand_query() → hybrid dense+BM25 → RRF fuse           (if use_structured_data — SQLite,
   → cross-encoder rerank → confidence label                sub-millisecond, STEP 16)
       ↓                                                             ↓
       └─────────────────────────────┬─────────────────────────────┘
                                      ↓
                     [build_messages()]  ← TRIAL DATA section (if any) placed
                                            before RETRIEVED SOURCES (STEP 7)
                                      ↓
                          [4-Tier LLM Waterfall]
                            Tier 1: Gemini 2.0 Flash (primary, 1M TPM free)
                            Tier 2a: Groq — Llama 3.3 70B
                            Tier 2b: Groq — Mixtral 8x7B
                            Tier 3: OpenRouter (auto-routes to best free model)
                            Tier 4: Together AI — DeepSeek R1 (last resort)
                                      ↓
                          Natural prose answer + DOI references
                                      ↓
                   [_verify_faithfulness()]  ← direct Gemini call, checks
                                                each claim against retrieved
                                                sources (STEP 13)
                                      ↓
                   [gene_validator.extract_gene_mentions() + validate_genes()]
                    ← runs unconditionally (free check), not gated by the
                      router's run_gene_validation flag (STEP 15)
                                      ↓
                          Answer + faithfulness footer (if flagged) +
                          gene verification footer (if genes mentioned) +
                          references  →  Gradio UI

6. STEP 3 — PDF PROCESSING PIPELINE  (src/pdf_processor.py)
================================================================================

CONCEPT: Why do we need to process PDFs?
  LLMs have a context window limit (how much text they can read at once). We
  cannot feed an entire 20-page paper into an LLM. Instead, we split every
  paper into small "chunks" of ~512 tokens (about 350 words each). Each chunk
  gets metadata tags (which paper it came from, which page, which section).
  Later, we only retrieve the top few chunks for a given question.

FILE: src/pdf_processor.py
CLASS: PDFProcessor

CONSTRUCTOR PARAMETERS:
  input_dir      — folder containing all PDFs (data/pdfs/)
  output_file    — where to save chunks (data/processed_chunks.json)
  log_file       — log file path
  chunk_size     — 512 tokens per chunk (roughly 350 words)
  chunk_overlap  — 128 tokens overlap between consecutive chunks (v2 upgrade)
  use_ocr        — True to enable OCR for scanned PDFs

--- TEXT EXTRACTION ---
  Method: extract_text_from_pdf()
  Uses PyPDF2.PdfReader to read each page.
  For each page, calls page.extract_text() which uses the PDF's embedded text
  layer (fast, no GPU needed).
  If a page has fewer than 50 characters of text AND use_ocr=True, it falls
  back to OCR using pytesseract (Tesseract OCR engine) on a 300 DPI image of
  that page. This handles scanned papers that have no embedded text.
  Each page's text is prefixed with "[PAGE N]" so we can track page numbers.

--- SECTION DETECTION (v2 upgrade) ---
  CONCEPT: Scientific papers have standard sections: Abstract, Introduction,
  Methods, Results, Discussion, Conclusion. If we know which section a chunk
  comes from, the retriever can weight results/methods chunks differently
  from introduction chunks. The section name is stored in each chunk's metadata.

  Implementation (pdf_processor.py:47-70):
    SECTION_PATTERNS — a list of (name, regex) tuples matching common headers:
      ("abstract",      r"^\s*(abstract)\s*$")
      ("introduction",  r"^\s*(introduction|background)\s*$")
      ("methods",       r"^\s*(materials?\s+and\s+methods?|...)\s*$")
      ("results",       r"^\s*(results?(\s+and\s+discussion)?)\s*$")
      ("discussion",    r"^\s*(discussion)\s*$")
      ("conclusion",    r"^\s*(conclusions?|summary)\s*$")
      ("references",    r"^\s*(references?|bibliography|...)\s*$")

  _COMPILED_SECTION_PATTERNS compiles these with re.IGNORECASE for speed.
  detect_section(line) checks each line against patterns and returns the
  section name if it matches, or None if it is body text.
  The current section is tracked across the whole document — when a new section
  header is found, the current chunk is flushed and the section label changes.
  Every chunk gets a "section" field with the label (e.g. "results").

--- TABLE DETECTION AND PRESERVATION (v2 upgrade) ---
  CONCEPT: Scientific papers contain tables with yield data, treatment comparisons
  etc. If we split a table mid-row, the LLM cannot read it. We detect table rows
  and keep the entire table as one chunk. This is also what makes Change 6's
  structured-data extraction (STEP 16) possible at all — it re-uses this exact
  same heuristic to find candidate chunks to extract numbers from.

  is_table_row(line) — returns True if the line contains "|" (markdown-style
    table) OR has 3+ consecutive spaces between tokens (PDF column alignment).

  group_table_blocks(lines) — scans all lines on a page and groups consecutive
    table rows into {"type":"table", "content": joined_rows} blocks.
    Non-table lines become {"type":"text", "content": single_line} blocks.

  In chunk_text(), when a table block is encountered:
    1. The current text chunk is flushed first (so the table is not mixed in)
    2. The entire table is stored as a single chunk (even if > 512 tokens)
    3. No overlap is added after tables (they are self-contained)

  KNOWN GAP THIS CREATES (see STEP 16): a table's caption — which usually
  states the location/year/study the numbers belong to — is text, so it ends
  up in a DIFFERENT chunk than the table itself. Change 6's extraction script
  works around this by also feeding the immediately-neighboring chunks to the
  LLM as context, but this chunk-boundary split is the root reason table
  extraction needs that workaround at all.

--- TOKEN-BASED CHUNKING ---
  CONCEPT: We count tokens (not characters) because LLMs measure context in
  tokens. One token ≈ 4 characters on average, but varies. We use tiktoken
  (OpenAI's tokenizer, cl100k_base encoding) for exact token counts.

  count_tokens(text) — uses tiktoken if available, else falls back to len/4.

  chunk_text() algorithm (pdf_processor.py:321-438):
    1. Split full text by [PAGE N] markers to track page numbers
    2. For each page, split into lines
    3. group_table_blocks() processes lines into text/table blocks
    4. For text blocks:
       a. Split sentences by .!? punctuation
       b. Check each sentence for section headers via detect_section()
       c. Accumulate sentences into current_chunk
       d. When current_chunk tokens + new sentence tokens > chunk_size:
          → flush the current chunk to the output list
          → carry the last 128 tokens forward as overlap into the next chunk
             (This is the _get_overlap_text() method)
    5. Table blocks always flush current chunk first, then emit table as-is

  OVERLAP CONCEPT (v2 upgrade, was 50 tokens in v1, now 128):
    Overlap ensures that a sentence which falls across a chunk boundary can
    still be found by queries that match either its beginning or its end.
    Example: "The mean yield of 2.4 t/ha observed under drought conditions..."
    If this sentence is split, both the chunk ending with it and the chunk
    starting with it contain the crucial phrase "yield of 2.4 t/ha".

--- CHECKPOINT SYSTEM ---
  Every 50 PDFs, the accumulated chunks so far are written to:
    data/checkpoint_{N}.json
  This means if the SLURM job is killed at hour 3, we don't lose all work.
  Files: data/checkpoint_50.json ... data/checkpoint_1050.json (21 files)

--- OUTPUT FORMAT ---
  Each chunk is a Python dict saved to data/processed_chunks.json:
  {
    "text":        "The mean yield of 2.4 t/ha was observed...",
    "source_file": "10.2135_cropsci2004.1799.pdf",
    "year_range":  "1961-2006",
    "chunk_id":    1234,
    "page_number": 5,
    "token_count": 487,
    "section":     "results"
  }

  Also saves data/processing_metadata.json with run statistics:
    total_pdfs, successful, failed, total_chunks, total_pages, ocr_used

  IMPORTANT for later steps: chunk_id resets to 0 for every PDF (it's a
  per-paper counter), so it is NOT a globally unique identifier. STEP 12
  (hybrid retrieval) relies on this fact being understood — it uses
  ChromaDB's own "chunk_{i}" id (i = row position across the WHOLE corpus)
  instead, wherever a global identifier is needed.

FINAL RESULT: 21,876 chunks from 1,067 PDFs

7. STEP 4 — EMBEDDING GENERATION  (src/generate_embeddings.py)
================================================================================

CONCEPT: What is a vector embedding?
  A sentence like "bean rust pustules on leaves" can be converted into a
  1024-dimensional number array (a vector) by a neural network trained on
  millions of sentences. Similar sentences produce similar vectors (close in
  1024-dimensional space). This is the key to semantic search — two chunks that
  discuss the same topic will have similar vectors even if they use different
  words.

FILE: src/generate_embeddings.py
CLASS: EmbeddingGenerator

EMBEDDING MODEL: BAAI/bge-large-en-v1.5  (upgraded from all-MiniLM-L6-v2 — see
  ERROR 11 below for why the switch happened and what it broke)
  - Produces 1024-dimensional vectors (was 384 with all-MiniLM-L6-v2)
  - 335M parameters (was 22M) — scores 64.2% on MTEB retrieval vs. MiniLM's
    56.3%, a large jump in retrieval quality since this is the single biggest
    lever on answer quality in the whole system
  - L2-normalized output: every vector has length = 1.0
    This means cosine similarity = dot product, which is the fastest comparison
  - ASYMMETRIC convention: BGE models are fine-tuned so that *queries* should be
    prefixed with an instruction string, but *documents/passages* should not.
    generate_embeddings.py embeds documents WITHOUT any prefix (correct — it
    only ever embeds passages). The query-side prefix is applied later, in
    retriever.py, at query time (see STEP 6 below).

GPU PROCESSING (V100):
  batch_size=16 means 16 chunks are embedded in one GPU forward pass
  (reduced from 32 — bge-large-en-v1.5 is ~15x larger than all-MiniLM-L6-v2,
  so a smaller batch keeps it comfortably inside V100 VRAM).

  Timing: ~21,876 chunks ≈ 3–5 minutes total on a V100 (was ~45 seconds with
  the old MiniLM model — bge-large-en-v1.5 is much slower per-chunk, but this
  only runs once per corpus rebuild, not per query).

PIPELINE (generate_embeddings.py:620-661):
  1. check_gpu()         — verify CUDA is available, log GPU name/memory
  2. load_model()        — download BAAI/bge-large-en-v1.5 (auto-downloads once)
  3. load_chunks()       — read data/processed_chunks.json
  4. generate_embeddings() — batch encode all texts, returning numpy array
  5. validate_embeddings() — check shape, no NaN/Inf, normalization, counts
  6. save_embeddings()   — save as data/embeddings.npy + data/embeddings_metadata.json
  7. print_statistics()  — log performance metrics

VALIDATION CHECKS:
  - Dimension check: every vector must be exactly 1024-dimensional
  - NaN check: corrupted embeddings fail silently without this check
  - Normalization check: vectors should have mean norm ≈ 1.0
  - Count check: number of embeddings must equal number of chunks

OUTPUT FILES:
  data/embeddings.npy
    Shape: (21876, 1024)  — float32 numpy array
    Size: ~85 MB (was ~33 MB at 384-dim)

  data/embeddings_metadata.json
    Contains per-chunk metadata (source_file, page_number, section, etc.)
    plus generation statistics (model, batch_size, GPU name, time, speed)

8. STEP 5 — VECTOR STORE + BM25 INDEX BUILDING  (src/build_vector_store.py)
================================================================================

CONCEPT: What is ChromaDB?
  ChromaDB is an open-source vector database. A vector database is like a
  normal database except:
    - Instead of searching by exact column values (name = "Smith"), you search
      by similarity (find all vectors close to this query vector)
    - ChromaDB uses HNSW (Hierarchical Navigable Small Worlds), a graph-based
      algorithm that finds approximate nearest neighbours in milliseconds even
      across 100,000 vectors — far faster than brute-force comparison

  We use chromadb.PersistentClient which writes the database to disk
  (vector_db/). This means we build it once on HPCC and then upload it to
  HuggingFace Datasets for the web app to download.

FILE: src/build_vector_store.py
CLASS: VectorStoreBuilder

COLLECTION NAME: "bean_research_docs"
  A ChromaDB collection is like a table in a relational database.
  All 21,876 chunks are stored in this single collection.

DATABASE STRUCTURE:
  Each document in ChromaDB stores three things:
    id         — "chunk_0", "chunk_1", ..., "chunk_21875"  (this is the
                 SAME global row position that STEP 12's BM25 index and RRF
                 fusion use as their shared identifier — it's not just an
                 internal ChromaDB detail, other code depends on it)
    embedding  — 1024-dimensional float vector (from embeddings.npy)
    document   — the raw chunk text (for displaying in answers)
    metadata   — dict: {source_file, year_range, page_number, section, ...}

BATCH INSERTION (batch_size=1000):
  Inserting 21,876 vectors one at a time is slow. We insert 1,000 at a time
  using collection.add(embeddings=..., documents=..., metadatas=..., ids=...).
  This fills the collection in ~22 batches.

METADATA FILTERING:
  ChromaDB supports WHERE filters. We use this to let users filter by time
  period:
    collection.query(query_texts=[...], where={"year_range": "2007-2026"})
  This returns only chunks from papers published in 2007-2026.

BM25 INDEX BUILD (Change 2 — added directly to this script, not a separate
  one, deliberately: both stores need to be built from the exact same
  in-memory chunk list, in the same run, so their row ordering can never
  drift apart):
  build_bm25_index(metadata_list, texts) — tokenizes every chunk with the
  SAME tokenize_bm25() function retriever.py uses at query time (they must
  stay identical or BM25 scores become meaningless), builds a
  rank_bm25.BM25Okapi index, and pickles {"bm25": ..., "metadata": [...]} to
  vector_db/bm25_index.pkl. Soft-fails (logs a warning, continues) if
  rank_bm25 isn't installed — BeanRetriever falls back to dense-only
  automatically if this file doesn't exist (see STEP 12).

PIPELINE (build_vector_store.py run(), current order):
  1. load_data()             — load embeddings.npy + metadata + processed_chunks
  2. create_database()       — create ChromaDB PersistentClient at vector_db/
                               delete and recreate collection if it exists
  3. add_to_database()       — insert all chunks in batches of 1000
  4. analyze_metadata()      — count year_range distribution, unique sources
  5. build_bm25_index()      — build and pickle vector_db/bm25_index.pkl (Change 2)
  6. calculate_database_size() — measure disk usage (now includes bm25_index.pkl)
  7. run_validation_queries() — test 4 query types to confirm DB works:
       a. Semantic search: "bean breeding techniques"
       b. Filtered search: "drought resistance" WHERE year_range='2007-2026'
       c. Direct ID lookup: get chunk_0
       d. Count check: collection.count() should equal total chunks

     IMPORTANT: queries a. and b. embed the test query text locally via a
     _embed_query() helper (BAAI/bge-large-en-v1.5, with the BGE query
     instruction prefix) and pass query_embeddings= to collection.query().
     They deliberately do NOT use collection.query(query_texts=...), because
     that falls back to ChromaDB's own default embedding function — a
     different, 384-dim model — which would raise a dimension mismatch against
     our 1024-dim stored vectors. See ERROR 11 below.
  8. save_statistics()       — write vector_db/database_statistics.json
  9. print_statistics()      — log final summary

OUTPUT:
  vector_db/
    chroma.sqlite3            — main index file (includes metadata + HNSW)
    *.bin                     — binary HNSW graph files for fast ANN search
    bm25_index.pkl            — BM25 keyword index (Change 2), ~few MB
    database_statistics.json  — run stats

  Database size: ~1 GB total (~875 MB before the bge-large-en-v1.5 upgrade —
  the increase comes from storing 1024-dim vectors instead of 384-dim ones).
  bm25_index.pkl and, if built separately, gene_index.pkl (STEP 15, ~8 MB in
  a real run) and trial_data.db (STEP 16, size depends on corpus coverage)
  are negligible additions on top of the ~1 GB ChromaDB store.

9. STEP 6 — RETRIEVAL SYSTEM  (src/retriever.py + hf_space/retriever.py)
================================================================================

CONCEPT: Multi-stage retrieval
  Retrieval is how we find the most relevant chunks for a user's question.
  As of Change 2 this is THREE stages, not two:
    Stage 0 (Hybrid):  Query both ChromaDB (dense) and BM25 (keyword) in
                       parallel, fuse the two ranked lists with Reciprocal
                       Rank Fusion. See STEP 12 for the full mechanics —
                       this section covers the dense side, which existed
                       before Change 2 and is unchanged by it.
    Stage 1 (Fast):    Ask ChromaDB for the 20 best matches via cosine similarity
                       This is approximate but very fast (milliseconds)
    Stage 2 (Precise): Re-score all fused candidates with a cross-encoder
                       The cross-encoder reads the question AND each chunk
                       together, giving a much more accurate relevance score
    Result:            Keep only the top-k (6 for the Space, 10 for batch
                       HPCC runs) chunks from the re-scored set

FILE: src/retriever.py
CLASS: BeanRetriever

--- SCIENTIFIC SYNONYM EXPANSION ---
  CONCEPT: Researchers use technical terminology. A user might type "rust"
  but the papers say "Uromyces appendiculatus" or "bean rust" or "uredinia".
  If we embed just the word "rust", the query vector won't fully match paper
  text that only uses the Latin name. We fix this by augmenting the query.

  SCIENTIFIC_SYNONYMS dict (retriever.py:23-81):
    Maps 40+ common query terms to their scientific aliases:
      "rust"     → ["bean rust", "Uromyces appendiculatus", "foliar rust", ...]
      "drought"  → ["water deficit", "water stress", "soil water", ...]
      "yield"    → ["seed yield", "grain yield", "pods per plant", ...]
      "bean"     → ["common bean", "Phaseolus vulgaris", "navy bean", ...]
      "bcmv"     → ["bean common mosaic virus", "BCMNV", "mosaic virus"]
      "gwas"     → ["genome-wide association", "association mapping", ...]
      ... (40+ entries total)

  expand_query(query) (retriever.py:91-117):
    Scans the user query for any synonym keys (case-insensitive).
    For each match, appends up to 2 alias terms to the query string.
    Caps at 6 extra terms total to avoid making the embedding too long.
    Example:
      Input:  "How does rust affect bean yield?"
      Output: "How does rust affect bean yield? bean rust Uromyces appendiculatus
               common bean Phaseolus vulgaris seed yield grain yield"
    The augmented query is then embedded — the embedding vector now "points
    toward" the scientific vocabulary used in the papers.

    IMPORTANT (Change 2): this expanded string is used for DENSE retrieval
    only. BM25 (STEP 12) deliberately gets the RAW, un-expanded query —
    expanding "yield" to include "seed yield grain yield productivity..."
    would make BM25 search for keywords unlikely to appear verbatim, which
    defeats the point of exact keyword matching. The query router (STEP 17)
    follows the same raw-vs-expanded principle when deciding what to send to
    structured_data.py.

--- CHROMADB QUERY ---
  _chromadb_query() generates the query embedding locally using
  SentenceTransformer.encode() with the SAME model used to index the chunks:
  BAAI/bge-large-en-v1.5 (upgraded from all-MiniLM-L6-v2 — ERROR 11 below).
  Then calls collection.query() with n_results=20.
  Returns 20 chunk dicts with: text, source, doi, year_range, page, section,
  distance (L2 distance in 1024-dim space, was 384-dim), rerank_score (None
  at this point), bm25_score (None at this point — filled in only if the
  hybrid fusion pass also finds this chunk, see STEP 12), and global_id (the
  integer parsed from ChromaDB's own "chunk_{i}" document id — this is what
  STEP 12's RRF fusion uses to tell whether a dense hit and a BM25 hit are
  the same underlying chunk).

  QUERY INSTRUCTION PREFIX: BGE models are fine-tuned asymmetrically — the
  query side gets a fixed instruction prefix, the document side does not.
  _chromadb_query() prepends BGE_QUERY_INSTRUCTION =
  "Represent this sentence for searching relevant passages: " to the
  (already synonym-expanded) query text before calling embedder.encode().
  Documents were embedded in generate_embeddings.py WITHOUT this prefix.
  Getting this backwards (or omitting it) doesn't crash anything — it just
  quietly gives worse retrieval than bge-large-en-v1.5 is capable of, since
  the model wasn't fine-tuned to treat query and passage text the same way.

  QUERY EMBEDDER LAZY-LOADING: retrieve()/retrieve_candidates() are called
  from several places (hf_space/app.py, deploy/app.py, qa_with_ollama.py,
  interactive_qa.py, eval_qa.py, eval_ragas.py). Only the two app.py files
  ever passed an explicit `embedder=` into BeanRetriever(); the rest
  constructed BeanRetriever(collection) with no embedder at all. Before the
  Change 1 embedding-model upgrade that was harmless (see ERROR 11 for the
  full story) — ChromaDB's own default embedding function happened to also
  be all-MiniLM-L6-v2. Fix: BeanRetriever now has a _load_embedder() method
  that lazily loads BAAI/bge-large-en-v1.5 itself the first time a query
  runs, if the caller didn't already supply one. Every caller above is fixed
  by this one change — none of them needed to be edited individually.

  DOI RECONSTRUCTION: _filename_to_doi(filename) converts stored filenames
  back to DOIs:  "10.2135_cropsci2004.1799.pdf" → "10.2135/cropsci2004.1799"
  This gives us the citation format used in answers. Also reused by
  build_gene_index.py, build_vector_store.py, and extract_structured_data.py
  wherever a source filename needs to become a citable DOI.

--- HYBRID RETRIEVAL (Change 2) — see STEP 12 for the full mechanics ---
  retrieve_candidates() now internally does: load BM25 index if present
  (lazy, _load_bm25()) → get dense candidates as above → if BM25 available,
  fuse via Reciprocal Rank Fusion (_hybrid_fuse()) → dedupe → return. If no
  BM25 index is found, falls back to dense-only exactly as before Change 2.
  This is fully automatic; no caller needs to know or request it.

--- CROSS-ENCODER RERANKING ---
  CONCEPT: The bi-encoder (bge-large-en-v1.5) embeds the question and chunks
  separately and compares them in vector space. This misses subtle word
  interactions.
  A cross-encoder reads the question and chunk TOGETHER in one pass, so it
  can understand phrases like "yield is NOT affected by rust at early stages" —
  the bi-encoder would give this high similarity to "yield" and "rust" queries
  even though the sentence says the opposite.

  Cross-encoder model: cross-encoder/ms-marco-MiniLM-L-6-v2
    - Trained on MS MARCO passage ranking dataset (Microsoft's search benchmark)
    - Reads (question, passage) pairs and outputs a relevance score
    - max_length=512 tokens
    - Loaded lazily (_load_cross_encoder is called only when first needed)
    - Unchanged by any of Changes 1-7 — it operates on raw text pairs, not
      embeddings, so it doesn't care which retrieval channel found each
      candidate or which embedding model produced the vectors

  rerank(query, candidates, top_k=6):
    Creates pairs: [(question, chunk1_text), (question, chunk2_text), ...]
    Calls cross_encoder.predict(pairs) → returns a score for each pair
    Sorts by score (descending) → returns top_k chunks
    Falls back to distance-based ordering if cross-encoder unavailable

--- DEDUPLICATION ---
  _deduplicate(chunks): removes chunks with the same (source_file, page_number)
  keeping the one with the lowest distance. Used for the dense-only fallback
  path, where every candidate has a real distance to sort by.

  _dedupe_keep_order(chunks): a second, order-preserving variant added in
  Change 2 for the hybrid-fusion path — it keeps the first occurrence per
  (source, page) rather than re-sorting by distance, because BM25-only
  candidates have distance=None and can't be meaningfully sorted against
  real distances. The candidates are already RRF-ranked by the time this
  runs, so "first occurrence" already means "best fused rank."

--- CONFIDENCE ASSESSMENT ---
  assess_confidence(chunks) (retriever.py:134-157):
  Examines the top chunks' distances to give a quality label:
    SUPPORTED         — best_distance ≤ 0.45 AND ≥3 relevant chunks
                        (very strong semantic match in the database)
    PARTIALLY_SUPPORTED — best_distance ≤ 0.65 AND ≥2 relevant chunks
    INFERRED          — best_distance ≤ 0.85 (moderate match)
    UNSUPPORTED       — best_distance > 0.85 (weak match, still attempt answer)

  Distance thresholds explained:
    With L2-normalized embeddings, L2 distance and cosine similarity relate as:
      cos_sim ≈ 1 - (dist² / 2)
    So distance 0.45 ≈ cos_sim 0.90 (very strong match)
    Distance 0.85 ≈ cos_sim 0.64 (moderate match)

  The confidence label is passed to the prompt builder, which adds a note
  for INFERRED/UNSUPPORTED questions telling the LLM that evidence may be weak.

  NONE-DISTANCE SAFETY (Change 2): BM25-only chunks have distance=None.
  assess_confidence() now has a small _dist() helper that treats None as
  worst-case (1.0) instead of crashing the comparison — this bug and its
  twins elsewhere are catalogued in ERROR 15.

  ⚠ KNOWN FOLLOW-UP NEEDED (still not done as of Change 7): these four
  threshold constants (0.45 / 0.65 / 0.85 / 1.10, also mirrored as
  SIMILARITY_HARD_CUTOFF=1.20 in hf_space/retriever.py and
  NO_MATCH_THRESHOLD=1.10 in hf_space/app.py and deploy/app.py) were
  empirically tuned against all-MiniLM-L6-v2's distance distribution. A
  different embedding model — especially one 15x larger and trained
  differently, like bge-large-en-v1.5 — will very likely produce a different
  distribution of L2 distances for the same corpus, so these exact cutoff
  values may no longer separate "strong match" from "weak match" the way
  they did before. Re-validate — e.g. by running eval_qa.py or eval_ragas.py
  (STEP 14) and checking the confidence_distribution in the output, or by
  manually inspecting distances for a few known-good vs. known-bad queries —
  before trusting the SUPPORTED/PARTIALLY_SUPPORTED/INFERRED/UNSUPPORTED
  labels at face value against the new vector store.

FULL PIPELINE — retrieve(query, top_k=6, n_candidates=20):
  1. expand_query(query)                              — dense side only
  2. retrieve_candidates(expanded, n_candidates=20)    — ChromaDB top-20,
                                                          fused with BM25 via
                                                          RRF if available (STEP 12)
  3. _deduplicate() or _dedupe_keep_order()            — depending on path
  4. rerank(query, candidates, top_k=6)                — cross-encoder top-6
  5. assess_confidence(ranked)
  Returns: (chunks, confidence_label)

10. STEP 7 — PROMPT ENGINEERING  (src/prompts.py + hf_space/prompts.py)
================================================================================

CONCEPT: What is prompt engineering?
  The LLM receives a text prompt — this is our only way to control its behaviour.
  Prompt engineering is the practice of writing prompts carefully to get the
  exact output format, citation style, and reasoning approach we want.

FILE: src/prompts.py (kept identical to hf_space/prompts.py on every change)

--- SYSTEM PROMPT (SYSTEM_PROMPT variable) ---
  The system prompt is sent at the start of every conversation and sets the
  LLM's "persona" and rules. Our system prompt specifies:

  WRITING STYLE rules:
    - Write in flowing paragraphs (not bullet lists) by default
    - Integrate citations naturally: "...yields of 2–3 t/ha under rainfed
      conditions (doi:10.1234/example, p.4)"
    - Use specific numbers, units, and percentages from the papers
    - If multiple papers agree, synthesise into one clear statement
    - If papers disagree, say so plainly in natural language
    - Use subheadings only if they genuinely aid clarity for multi-part questions
    - Use markdown tables ONLY when the question asks for comparison AND there
      is enough actual data to fill the table meaningfully

  TABLE RULES (strict):
    - Only include a row if the source explicitly reports a value for it
    - NEVER leave cells empty or write "not reported"
    - Every data cell must have a real number from a source
    - Keep tables small and accurate — 3 accurate rows > 8 rows with empty cells
    - Always follow a table with a summary paragraph

  CITATION RULES (strict):
    - Cite ONLY using DOI format: (doi:10.XXXX/suffix, p.N)
    - NEVER use [1], [2], [Source 1], [Document 2] — these are FORBIDDEN
    - Only cite when it directly supports the specific claim in that sentence
    - Sources marked "WEAK EVIDENCE" only cited when no stronger source exists

  TRIAL DATA rules (added Change 7, when a TRIAL DATA section is present):
    - Trial data rows are exact numbers for the specific cultivar/location/year
      asked about — prefer them over paraphrasing a similar number from a
      retrieved passage
    - These rows were extracted automatically from paper tables and may
      occasionally contain transcription errors (see STEP 16) — cite them the
      same doi/page way as any other source so the user can check the original
    - Use the literature sources to explain what the trial numbers mean and how
      they compare to other findings — trial data gives precision, literature
      gives interpretation

  IMPORTANT behaviour:
    - Never refuse to answer — give best answer from available sources
    - If sources only partially address the question, answer what is possible
    - Do NOT mention confidence labels or retrieval systems in the answer

  WHY NO CONFIDENCE LABELS IN THE ANSWER:
    Earlier versions showed labels like [SUPPORTED] or [INFERRED] in the answer
    text. Users found this confusing ("wtf is this labels"). The confidence
    assessment is still done internally (for routing and prompt notes) but is
    never shown to users.

--- SECTION TAGS ---
  SECTION_TAG_MAP maps section names to display tags:
    "results"     → "[RESULTS]"
    "methods"     → "[METHODS]"
    "discussion"  → "[DISCUSSION]"
    etc.
  These tags are prepended to each chunk in the context block sent to the LLM,
  so the LLM knows whether evidence comes from a methods section vs. results.

--- BUILD_CONTEXT() ---
  build_context(chunks) formats the retrieved chunks into a numbered list:
    [1] doi:10.2135/cropsci2004.1799 | p.5 | [RESULTS]
    <chunk text here>

    [2] doi:10.1007/s00122-020-03567-8 | p.3 | [METHODS]
    <chunk text here>
    ...
  Chunks with distance > 0.85 get "⚠ WEAK EVIDENCE" appended to their header.
  Since Change 2, distance may be None (BM25-only chunk) — treated as
  worst-case (1.0) rather than crashing (see ERROR 15).

--- BUILD_MESSAGES() ---
  build_messages(question, chunks, confidence="", trial_data_block="")
  assembles the full prompt:
    [{"role": "system", "content": SYSTEM_PROMPT},
     {"role": "user",   "content": "<trial_data_block>\n\nRETRIEVED SOURCES:
                                     \n\n<context>\n\nQUESTION: ..."}]
  For INFERRED/UNSUPPORTED confidence, adds a note to the user message:
    "NOTE: The retrieved sources may only partially address this question.
     Answer as fully as you can from the evidence, and briefly note any gaps."

  trial_data_block (Change 7): a PRE-FORMATTED string — the caller is
  expected to have already called structured_data.format_trial_results(rows)
  and pass the resulting string in, or "" if the query router (STEP 17)
  didn't activate structured data for this question. prompts.py deliberately
  does not know the row schema; it only knows where to place the block
  (before "RETRIEVED SOURCES:") so the LLM sees exact numbers distinctly from
  paraphrased literature text.

--- BUILD_OLLAMA_PROMPT() ---
  Alternative for Ollama (local LLM) which uses llama3 instruct format with
  special tokens: <|begin_of_text|><|start_header_id|>system<|end_header_id|>
  Takes the same trial_data_block parameter as build_messages(), placed the
  same way (before RETRIEVED SOURCES).

--- FORMAT_REFERENCES() ---
  format_references(chunks, titles=None) generates the reference list shown
  below the answer. UPDATED (Change 10, STEP 20): takes an optional
  `titles: {source_file: title}` lookup (data/paper_titles.json,
  LLM-extracted by scripts/extract_paper_titles.py — the same lookup that
  powers the GraphRAG paper-graph's node labels, Change 9). When a chunk's
  source paper has a known title, it's now shown as the link text instead
  of a bare DOI:
    **References:**
    • Genetic mapping of resistance loci in common bean (doi:10.2135/cropsci2004.1799)
    • doi:10.1007/s00122-020-03567-8 *(weak evidence)*
  (second entry falls back to the original bare-DOI format — its paper
  isn't in the titles lookup, e.g. outside the 964-paper GraphRAG corpus).
  Deduplicates by DOI — each paper appears only once even if multiple chunks
  from it were retrieved. Same None-distance safety fix as build_context().

  Separately, linkify_citations(answer) (also prompts.py, both copies) turns
  the LLM's inline "(doi:X, p.N)" citations (see CITATION RULES above —
  deliberately not [1]/[2], since a DOI the model writes is always one it
  actually saw in context, while a bracket number can be invented) into a
  clickable "([p.N](https://doi.org/X))" — applied to the model's output
  after generation, a pure display transform that doesn't change what gets
  cited or how the LLM decides to cite it.

11. STEP 8 — LOCAL QA TESTING ON HPCC  (src/qa_with_ollama.py)
================================================================================

CONCEPT: Why test locally before deploying?
  Before deploying to the internet (HuggingFace Spaces), we test the QA system
  on HPCC using Ollama — a tool that runs LLMs locally on our GPU.

OLLAMA SETUP:
  scripts/setup_ollama.sh downloads and installs Ollama to models/
  scripts/download_llama_model.sh runs: ollama pull llama3.1:8b
  scripts/start_ollama.sh starts the Ollama server: ollama serve
  The server listens on localhost:11434

  Model used: llama3.1:8b (Meta's Llama 3.1, 8 billion parameters)
    Requires ~6GB VRAM — fits comfortably on the V100's 32GB

INTERACTIVE QA:
  python src/interactive_qa.py
  Opens a command-line loop:
    Question> How does drought affect bean yield?
    ...answer with citations...
    Question> /quit to exit, /help for commands (/year, /sources, /strict —
              the old /hybrid command was removed in Change 2 since hybrid
              retrieval is now automatic, not a toggle)

WHAT ANSWER_QUESTION() DOES (rewritten for Change 7 — query routing):
  1. query_router.route(question) → RoutingDecision: use_literature (~always
     True), use_structured_data, run_gene_validation, plus the actual
     matched cultivar/location/trait/year/gene entities (see STEP 17)
  2. Literature retrieval (retriever.retrieve()) and structured-data lookup
     (structured_data.query_trial_data(), if flagged) run CONCURRENTLY via
     concurrent.futures.ThreadPoolExecutor — they're independent of each
     other, so there's no reason to serialize them (both are individually
     fast: SQLite is sub-millisecond, vector retrieval is sub-second, but
     structuring the code this way keeps the independence explicit and
     leaves room for real gains if either grows more expensive later)
  3. If strict_evidence is set AND confidence is UNSUPPORTED AND no trial
     data rows were found, short-circuit with "Insufficient evidence..." —
     changed in Change 7 to check trial_rows first: structured data can carry
     the answer even when literature-only confidence looks weak
  4. build_ollama_prompt(question, chunks, confidence, trial_data_block=...)
     → formatted prompt, trial data section included if activated
  5. HTTP POST to localhost:11434/api/generate → answer text
  6. Gene validation runs UNCONDITIONALLY on the answer (not gated by
     run_gene_validation — see STEP 15/17 for why): extract_gene_mentions(answer)
     → validate_genes(mentions) if any found
  7. Return: {answer, confidence, routing, trial_data_rows, gene_checks,
     sources, retrieval_time_s, generation_time_s}

  eval_qa.py and eval_ragas.py both call this same function, so they inherit
  routing, structured data, and gene validation automatically without any
  changes of their own.

12. STEP 9 — EVALUATION BENCHMARK  (src/eval_qa.py + benchmark_questions.py)
================================================================================

CONCEPT: How do we know if the system is working well?
  We need objective measures. eval_qa.py runs a fixed set of pre-written
  questions with known expected answer elements (rubrics) and scores the
  system's answers by keyword coverage. See STEP 14 for the LLM-judged RAGAS
  metrics that supplement this coarse scoring.

FILE: src/eval_qa.py (scoring logic)
FILE: src/benchmark_questions.py (the question bank — Change 4, SHARED with
  eval_ragas.py so the two evaluators never drift onto different question sets)

75 BENCHMARK QUESTIONS in 7 categories (was 25 in 5 categories before Change 4):
  1. Direct Lookup (10, IDs: DL-01 to DL-10)
     Facts stated verbatim in a single paper.
  2. Cross-Section Synthesis (10, IDs: CS-01 to CS-10)
     Facts assembled from multiple papers/sections.
  3. Inference / Cause-Effect (10, IDs: IN-01 to IN-10)
     Answer follows logically but is not stated directly.
  4. Critique / Limitations (10, IDs: CR-01 to CR-10)
     Asks for limitations, gaps, or challenges.
  5. Multi-Part Questions (10, IDs: MP-01 to MP-10)
     Compound questions requiring multiple sub-answers.
  6. Adversarial (10, IDs: AD-01 to AD-10) — NEW in Change 4. Fake gene IDs
     (Phvul.011G999950), fake cultivars ("Sierra Crimson-9"), out-of-scope
     topics phrased like bean questions (wholesale bean pricing, ornamental
     gardening). The "correct" answer is honest uncertainty, not a confident
     (necessarily fabricated) fact. This is exactly where RAGAS's faithfulness
     metric (STEP 14) is more useful than keyword rubrics: a fabricated answer
     about a fictional gene has near-zero faithfulness regardless of how
     confident it sounds.
  7. Multi-Hop Synthesis (15, IDs: MH-01 to MH-15) — NEW in Change 4. Require
     synthesizing across 3+ distinct sub-topics/papers, deeper than
     cross_section's typical 2-source asks.

  IMPORTANT CAVEAT (documented in benchmark_questions.py itself): questions
  DL-06 through MH-15 (everything beyond the original 25) were authored in
  the same style/domain as the originals but NOT verified against actual
  corpus content — they may turn out to be unanswerable from what's actually
  indexed. ground_truth (needed for RAGAS's context_recall, STEP 14) was
  None for every question until Change 11, which populated 11 of 75 by
  actually searching data/processed_chunks.json for real supporting text —
  see STEP 14's entry for exactly which and the module docstring for the
  full per-question rationale. Fabricating the other 64 without verified
  access to the papers would produce evaluation numbers that look rigorous
  but rest on guesses, so they remain None deliberately.

SCORING (score_answer function, src/eval_qa.py):
  rubric_coverage — fraction of rubric keywords found in the answer text
    (coarse heuristic: checks if any 3+ char non-stopword from each rubric item
     appears in the answer)
  has_doi_citation — True if answer contains "doi:10.XXXX" pattern
  has_confidence_label — True if answer contains [SUPPORTED] etc. (should be
    False in current version since we removed confidence labels from outputs)
  retrieval_confidence — SUPPORTED/PARTIALLY_SUPPORTED/INFERRED/UNSUPPORTED
  confidence_appropriate — NEW in Change 4: for adversarial questions only
    (expect_low_confidence=True in benchmark_questions.py), whether the
    system actually hedged (INFERRED/UNSUPPORTED) rather than confidently
    answering about a fabricated gene/cultivar/out-of-scope topic. None for
    every non-adversarial question.

AGGREGATE REPORTING:
  avg_rubric_coverage           — mean coverage across all questions
  doi_citation_rate             — fraction of answers with at least one DOI
  confidence_label_rate         — fraction incorrectly showing confidence labels
  adversarial_appropriate_hedge_rate — NEW: fraction of adversarial questions
    where the system appropriately expressed low confidence
  by_category                   — average rubric coverage per category
  confidence_distribution        — how many SUPPORTED/PARTIAL/INFERRED/UNSUPPORTED

Output saved to data/eval_results.json (or --output path)

⚠ PRE-Change-4 HISTORY (see ERROR 13): eval_qa.py's score_answer() called
  re.findall()/re.search() but the module never imported the `re` module at
  all. Every single run of this script, since it was first written, crashed
  with NameError on the first scored question — meaning no automated
  benchmark run had ever actually completed before this was found and fixed.
  Any historical claim about this system's quality prior to Change 4 was
  based on manual spot-checking, not this script's output.

--- APP.PY STARTUP SEQUENCE ---
  When HF Spaces starts the container and runs app.py, the top-level code
  (outside functions) executes immediately:

  1. Load embedding model:
     embedder = SentenceTransformer("BAAI/bge-large-en-v1.5")
     (upgraded from "sentence-transformers/all-MiniLM-L6-v2" — see STEP 4 and
     ERROR 11). This downloads ~1.3GB from HuggingFace Model Hub (cached after
     first download; was ~90MB for MiniLM, so cold starts and any HF Space
     ephemeral-storage wipes now cost more download time). Used to embed user
     queries — and, via _search_communities(), the GraphRAG global-mode query
     — at runtime.

  2. Download vector database:
     DB_PATH = snapshot_download(
         repo_id="Parimalanath/bean-lab-vector-db",
         repo_type="dataset",
         local_dir="/tmp/vector_db",
     )
     snapshot_download is smart: it only downloads files that aren't already
     in /tmp/vector_db. This pulls down EVERYTHING in the dataset repo —
     chroma.sqlite3, bm25_index.pkl, gene_index.pkl, trial_data.db — as one
     download; none of Changes 2/5/6 required any change to this call. This
     is why we moved the vector_db OUT of the Space repo and into a separate
     HF Dataset repo in the first place — see STEP 11 and ERROR 5.

  3. Load ChromaDB, gene index, trial database, BM25 index — all via each
     module's own lazy-loader (BeanRetriever._load_bm25(), gene_validator's
     _load_index(), structured_data's _load_db()), each trying
     /tmp/vector_db/<file> among its candidate paths. None of these block
     each other or app.py startup — if any file is missing, that subsystem
     silently degrades (dense-only retrieval, no gene verification, empty
     structured-data results) rather than crashing the app.

  4. Create retriever:
     retriever = BeanRetriever(collection, embedder=embedder)
     retriever._load_cross_encoder()   ← downloads ms-marco-MiniLM-L-6-v2

--- QUERY ROUTING + PARALLEL RETRIEVAL (Change 7) ---
  Inside chat()'s local-mode branch, immediately before retrieval:
    decision = route(message)   ← rule-based, on the RAW current message,
                                   not the conversation-augmented context_query
                                   used for retrieval itself (see STEP 17)
  Then literature retrieval and (if decision.use_structured_data) the
  structured-data query run concurrently:
    with ThreadPoolExecutor(max_workers=2) as executor:
        lit_future = executor.submit(retriever.retrieve, context_query, ...)
        struct_future = executor.submit(query_trial_data, ...) if activated else None
        chunks, confidence = lit_future.result()
        trial_rows = struct_future.result() if struct_future else []
  chat() is a plain synchronous generator (not async def) — ThreadPoolExecutor
  is the right tool here specifically BECAUSE there's no async context to
  plug into; both calls are I/O-bound (SQLite read, HTTP-backed ChromaDB
  query) so threads give real concurrency despite the GIL.

  The out-of-scope gate was also changed in Change 7: a question is only
  rejected as "I couldn't find relevant papers" if BOTH literature retrieval
  found nothing relevant (_out_of_scope(chunks)) AND no structured trial-data
  rows were found. Before this, a narrow "yield of X in Y" question could be
  rejected purely because no literature chunk happened to mention that exact
  combination, even when trial_data.db had the exact answer.

--- PER-USER RATE LIMITER ---
  WHY: HF Spaces is public. If someone writes a script that sends 1000 requests
  per minute, they could exhaust all LLM API quotas for everyone.

  Implementation:
    RATE_LIMIT_REQUESTS = 8     (max 8 questions)
    RATE_LIMIT_WINDOW   = 60    (per 60 seconds)

    _rate_lock = threading.Lock()
    _user_log = {}  (session_hash → list of timestamps)

  Why threading.Lock():
    Gradio's ASGI server handles multiple users concurrently in different threads.
    Without a lock, two threads could simultaneously read and modify
    _user_log and corrupt the data (race condition).
    threading.Lock() ensures only one thread touches the dict at a time.

  Why session_hash and not IP address:
    Multiple researchers at MSU may share the same IP (university NAT).
    session_hash is unique per browser tab, so colleagues don't block each other.

--- 4-TIER LLM WATERFALL ---
  WHY: Free-tier AI APIs frequently return HTTP 429 (rate limited) or
  HTTP 503 (server overloaded). If we rely on a single API, the app fails
  constantly. By chaining 4 services, the probability that ALL fail at once
  is extremely low. The user never sees an error in normal operation.

  call_llm(messages) orchestrates the waterfall:

  TIER 1: Gemini 2.0 Flash — _call_gemini()
    Primary because Google gives 1,000,000 tokens/minute free. Also the
    model used directly (bypassing the rest of the waterfall) for the
    faithfulness check (STEP 13) and as the RAGAS judge LLM (STEP 14) — see
    STEP 26 for why those two calls use Gemini specifically, not call_llm().
    Uses direct requests.post() to:
      https://generativelanguage.googleapis.com/v1beta/models/
      gemini-2.0-flash:generateContent?key={GEMINI_API_KEY}
    temperature=0.1 makes answers more deterministic and factual.
    Falls through to Tier 2 on HTTP 429, 500, or 503.

  TIER 2a: Groq — Llama 3.3 70B — _call_groq(messages, GROQ_MODEL_PRIMARY)
    Groq runs LLMs on LPUs (Language Processing Units) — specialized chips that
    are much faster than GPUs for inference. Free tier: 6000 tokens/minute.
    Falls through on HTTP 413 (request too large), 429, or 503.

  TIER 2b: Groq — Mixtral 8x7B — _call_groq(messages, GROQ_MODEL_FALLBACK)
    If the 70B model hits its per-minute limit, try the smaller Mixtral model.

  TIER 3: OpenRouter Auto — _call_openrouter()
    Dynamically picks the best available free model from its network.

  TIER 4: Together AI — DeepSeek R1 — _call_together()
    Last resort — if this fails too, the user sees an error message listing
    all 4 failure reasons.

  WHY WE USE requests.post() INSTEAD OF OPENAI SDK or GROQ SDK:

15. STEP 12 — HYBRID BM25 + RRF RETRIEVAL  (Change 2)
================================================================================

See HYBRID_RAG_UPGRADE.md for the full narrative version of this section —
it was rewritten from scratch for Change 2 and is kept as the canonical
"why hybrid retrieval works this way" document. Summary here for completeness:

WHAT REPLACED WHAT:
  An earlier, opt-in hybrid system (`--hybrid` flag, `data/bm25_index.json`,
  `HybridBeanRetriever` class, `/hybrid on` CLI command, `src/bm25_index.py`,
  `src/build_bm25_index.py`, `src/hybrid_retriever.py`,
  `jobs/build_bm25_index.sb`, `jobs/run_ollama_qa_hybrid.sb`) was DELETED
  entirely and replaced by what's described below. That old system was also
  silently non-functional on HPCC the whole time it existed — it imported
  functions from `retriever` that only existed in hf_space/retriever.py, not
  src/retriever.py, and every call site swallowed that ImportError.

HOW THE CURRENT SYSTEM WORKS:
  1. BUILD (build_vector_store.py, STEP 5): tokenize every chunk with
     tokenize_bm25() (lowercase, splits on hyphens, keeps dots inside
     alphanumeric runs so gene IDs and decimals survive as one token), build
     a rank_bm25.BM25Okapi index, pickle to vector_db/bm25_index.pkl
     alongside chroma.sqlite3 — same script, same in-memory chunk list as
     ChromaDB, so the two can never drift out of row-order sync.
  2. QUERY (retriever.py, both copies): BeanRetriever._load_bm25() lazily
     loads the pickle on first query (candidate paths: vector_db/bm25_index.pkl,
     /tmp/vector_db/bm25_index.pkl, or $BEAN_BM25_INDEX). If not found,
     silently falls back to dense-only — every caller gets this automatically,
     no flag required.
  3. FUSION: raw query → BM25.get_scores() → top-N by score. Expanded query
     (expand_query()) → ChromaDB → top-N by distance. Reciprocal Rank Fusion:
     rrf_score(doc) = Σ 1/(60 + rank) across whichever list(s) contain it.
     The shared identifier across both lists is the integer parsed from
     ChromaDB's "chunk_{i}" id (_parse_chroma_id()) — NOT the per-chunk
     "chunk_id" metadata field, which resets to 0 for every PDF (see STEP 3)
     and can't identify a chunk globally.
  4. The fused, deduplicated (_dedupe_keep_order()) candidate list then goes
     through the SAME cross-encoder reranking as always (STEP 6) — reranking
     doesn't know or care which channel found each chunk.

BUGS THIS SURFACED (full detail in ERROR 15): several places compared a
  chunk's `distance` against a numeric threshold using `.get("distance", 1.0)`,
  which returns None — not the default — when distance is explicitly None
  (every BM25-only chunk). Fixed in assess_confidence(),
  apply_similarity_threshold() (hf_space/retriever.py only — src/retriever.py
  never had this function), build_context(), format_references(), and the
  _out_of_scope() gate in both hf_space/app.py and deploy/app.py.

DEPENDENCY: rank-bm25 (pure Python, no compiled deps) — in requirements.txt
  and hf_space/requirements.txt.

16. STEP 13 — FAITHFULNESS VERIFICATION / SELF-RAG LITE  (Change 3)
================================================================================

CONCEPT: The system generates an answer and, until Change 3, simply trusted
  it. Nothing checked whether the LLM actually stayed faithful to the
  retrieved context — a second LLM call, done cheaply, can catch cases where
  it didn't.

FILE: hf_space/app.py originally (Change 3); ALSO deploy/app.py as of
  Change 16 (see that section below) — still NOT the HPCC batch path
  (qa_with_ollama.py/eval_qa.py/eval_ragas.py), which asks each benchmark
  question independently by design and was never in scope for this.

HOW IT WORKS: _verify_faithfulness(context, answer) — STALE HERE UNTIL NOW:
  this used to read _verify_faithfulness(chunks, answer); Change 9a
  refactored the parameter to plain context: str so the SAME function could
  serve both hf_space/app.py's local mode (build_context(chunks)) and
  global mode (the community-summary string) without local mode's chunk
  list leaking into a function that has no reason to know chunk internals
  — see STEP 19's Change 9a section for the full reasoning. This doc's own
  STEP 13 text was never updated to match at the time; fixed here.
  1. Builds a prompt: "Given these source passages: {context}
     ... And this generated answer: {answer} ... For each factual claim,
     determine SUPPORTED / UNSUPPORTED / CONTRADICTED ... Return ONLY a JSON
     object: {"claims": [{"text": ..., "verdict": ...}]}"
  2. Calls _call_gemini() DIRECTLY — not the full 4-tier call_llm() waterfall.
     Deliberate: this is a cheap secondary check, not worth spending the
     scarcer Groq/OpenRouter/Together free-tier quota on if Gemini happens to
     be down. If Gemini fails, the check is skipped silently (soft-fail) —
     it must never block the user from seeing their primary answer.
  3. Parses the response defensively: regex-extracts the first {...} JSON
     object from the raw text (handles stray prose/markdown fences the LLM
     might add), then json.loads(). Any parse failure → skip silently.
  4. If any claim is UNSUPPORTED or CONTRADICTED, appends a warning footer:
     "⚠️ Automated faithfulness check — the following claim(s) could not be
     verified against the retrieved sources: - *Unsupported:* ..."

WHY A FOOTER, NOT "STRIPPING" THE CLAIM (the original design allowed either):
  The checker returns each claim as the LLM's OWN extraction/paraphrase of
  text from the answer — it is NOT guaranteed to be a verbatim substring of
  the answer. A naive answer.replace(claim_text, "") would frequently
  silently no-op on paraphrased claims, giving false confidence that a
  hallucination was removed when it wasn't. Appending a visible warning is
  slower to read but can't silently fail the way string-surgery can.

COST NOTE: the original estimate was ~500 tokens per check. Realistically,
  TOP_K=6 chunks of context + the answer + the JSON claims list runs closer
  to 1500-2200 tokens round-trip — still trivial against Gemini's 1M TPM
  free tier, just a more honest number than the original estimate.

17. STEP 14 — RAGAS EVALUATION PIPELINE  (Change 4, src/eval_ragas.py)
================================================================================

CONCEPT: eval_qa.py's keyword-rubric scoring (STEP 9) is coarse — it can't
  tell if an answer said the right thing in the wrong words, or the wrong
  thing using the right keywords. RAGAS computes LLM-judged metrics instead.

FILE: src/eval_ragas.py
SHARES: src/benchmark_questions.py (same 75 questions as eval_qa.py, STEP 9)

METRICS COMPUTED:
  faithfulness              — does the answer only contain claims supported
                              by the retrieved context? No ground truth needed.
  answer_relevancy           — does the answer address the question? Needs
                              embeddings but no ground truth.
  context_precision_no_ref   — are the retrieved chunks actually relevant?
                              Computed via RAGAS's LLMContextPrecisionWithoutReference,
                              which uses the generated ANSWER as the relevance
                              yardstick instead of a ground-truth reference.
                              Runs on every question.
  context_precision          — the reference-based variant of the above.
  context_recall             — did retrieval capture everything needed?
                              REQUIRES a ground_truth reference answer.

  context_precision and context_recall are computed ONLY for questions with
  a non-empty ground_truth in benchmark_questions.py — 11 of 75 as of
  Change 11 (all 7 direct_lookup and 4 of 10 cross_section questions with
  clean corpus support: DL-01, DL-03, DL-04, DL-07, DL-08, DL-09, DL-10,
  CS-01, CS-02, CS-09, CS-10). These were populated by actually searching
  data/processed_chunks.json (21,876 chunks, real text from the 964 indexed
  papers) for verifiable supporting passages — not authored from general
  domain knowledge, which was exactly what STEP 9's original caveat refused
  to do without that access. The remaining 3 direct_lookup-adjacent topics
  that looked plausible up front (soil pH range, herbicide product names,
  deficit-irrigation WUE) and 6 more cross_section topics turned up no
  clean, bean-specific match after real searching and were deliberately
  left None — this crop-science-journal corpus simply doesn't cover some
  agronomy-extension-style facts. See benchmark_questions.py's docstring
  (item 1) for the full per-question breakdown of what's populated and why
  the rest isn't yet.

JUDGE MODEL: Gemini 2.0 Flash (free), via langchain_google_genai.ChatGoogleGenerativeAI
  wrapped in ragas.llms.LangchainLLMWrapper. Embeddings for answer_relevancy
  use the SAME model as the rest of the system (BAAI/bge-large-en-v1.5) via
  langchain_community.embeddings.HuggingFaceEmbeddings, wrapped in
  ragas.embeddings.LangchainEmbeddingsWrapper — avoids any OpenAI dependency.

DEPENDENCY FRAGILITY (see STEP 26 for the exact pinned versions): ragas,
  langchain-community, and langchain-google-genai have real, verified
  version conflicts with each other outside a narrow compatible window —
  confirmed by actually installing combinations in an isolated venv, not by
  reading changelogs. ragas 0.2.x requires langchain-core<0.4; recent
  langchain-google-genai releases require langchain-core>=1.0. The pinned
  set (ragas==0.2.15, langchain-community==0.3.7, langchain-google-genai==2.0.11)
  is the one actually verified to resolve and import together — don't bump
  any of these three individually without re-checking.

PIPELINE (eval_ragas.py main()):
  1. Load the 75-question benchmark (optionally filtered by --categories,
     capped by --limit for smoke testing)
  2. For each question, call qa_with_ollama.answer_question() — the SAME
     production pipeline (routing, hybrid retrieval, gene validation) that
     batch QA and the interactive CLI use; nothing about the pipeline is
     reimplemented here
  3. Build a ragas.EvaluationDataset of SingleTurnSample objects
     (user_input, retrieved_contexts, response, and reference= only for
     questions with ground_truth)
  4. Run ragas.evaluate() twice: once with the reference-free metrics over
     ALL answered questions, once with the reference-based metrics over only
     the ground_truth subset (11 of 75 questions as of Change 11)
  5. Merge per-question, save to data/ragas_results.json with a timestamp,
     aggregate scores, and by-category breakdowns

USAGE:
  export Googlegeminiapi=<your-gemini-api-key>
  python3 src/eval_ragas.py \
      --vector-db vector_db \
      --output data/ragas_results.json \
      --log-file logs/ragas_eval.log

SCHEDULING "nightly or on every code change": there is no CI system in this
  repository (no .github/workflows, not even confirmed as a git repo at the
  project root) — running this on a schedule requires your own HPCC crontab
  calling `sbatch jobs/run_ragas_eval.sb`, or a CI system set up separately.
  Not something this codebase configures on its own.

18. STEP 15 — GENE/LOCUS VALIDATION  (Change 5, src/gene_validator.py)
================================================================================

CONCEPT: After the LLM generates an answer, check any gene/locus names it
  mentions against real databases — catches a hallucinated gene name before
  it reaches the user, the same spirit as the faithfulness check (STEP 13)
  but specifically for gene nomenclature.

FILES: src/gene_validator.py (extraction + validation), src/build_gene_index.py
  (offline index builder), copied identically to hf_space/ for both.

★ THE FINDING THAT SHAPED THIS DESIGN (verified directly against the live
  NCBI and UniProt APIs before writing any code — not assumed): classical
  bean genetics symbols — Co-1 through Co-14 (anthracnose resistance),
  Phg-1 through Phg-4 (angular leaf spot), bc-1/bc-2/bc-3 (BCMV/BCMNV
  resistance), fin/Ppd (growth habit/photoperiod) — are essentially ABSENT
  from both NCBI Gene and UniProt for P. vulgaris. Concretely:
  `Co-1[Gene Name] AND txid3885[Organism]` on NCBI returns 0 of 62,308+
  P. vulgaris gene records; UniProt `gene:bc-3`, `gene:Fin` for
  organism_id:3885 return 0 results; a full-text search for "anthracnose"
  across all P. vulgaris NCBI gene records returns 0 hits. NCBI's P. vulgaris
  gene set is almost entirely systematic genome-annotation identifiers
  (LOC137819210, PHAVU_010G111100) — these databases don't catalog classical
  linkage-mapped genetics nomenclature from breeding literature at all.
  Flagging every mention of a real, decades-documented gene like Co-1 as
  "not found — treat with caution" would be actively backwards: it implies
  the SYSTEM is untrustworthy when the DATABASES just don't cover this
  vocabulary. Hence the three-way (not two-way) labeling below.

ALSO VERIFIED: NCBI does not store the Phytozome "Phvul.010G111100" dotted
  format at all — it cross-references the same locus as "PHAVU_010G111100"
  (dot removed, underscore inserted, no case change). gene_validator.py's
  _normalize_phytozome_id() converts one to the other before lookup.

THREE-WAY VALIDATION SOURCES:
  1. NCBI Gene + UniProt (build_gene_index.py) — for systematic genome-model
     IDs and protein/gene names that ARE catalogued. Verified end-to-end with
     a real download: 1.5GB gene_info.gz streamed and filtered to taxid 3885
     (34,174 records), UniProt's P. vulgaris subset via /stream (32,887
     entries), pickled to an 8.4MB vector_db/gene_index.pkl.
  2. CLASSICAL_GENE_SYMBOLS (a small, hand-curated allowlist in
     gene_validator.py itself — Co-1..14, Phg-1..4, bc-1/2/3/u, I, Ur-3/4/5/
     6/7/9/11/12/13, fin/Fin, Ppd) — labeled "classical_literature" in
     results, explicitly NOT claimed to be independently verified the way an
     NCBI/UniProt hit is. Documented as possibly incomplete; add entries as
     gaps are found.
  3. Neither → "not found", genuinely unverified.

EXTRACTION PATTERNS (extract_gene_mentions(), favors precision over recall
  deliberately — a missed mention costs nothing, a false one is misleading):
  - Phvul.\d{3}G\d{5,6} / PHAVU_\d{3}G\d{5,6}g? — Phytozome/NCBI gene models
  - Co-(1-14), Phg-(1-4), bc-(1-3), Ur-(3,4,5,6,7,9,11,12,13) — word-boundary
    regex, case-insensitive
  - Fin/fin/Ppd — ONLY counted if a biology keyword (gene, allele, locus,
    QTL, resistance, determinate, photoperiod, etc.) appears within 60
    characters — bare "P" and bare "I" (the BCMV "I" gene) are deliberately
    never matched at all, even context-anchored, since single-letter symbols
    are too ambiguous in free-flowing prose
  - Generic markdown-emphasized tokens (*PvTFL1y*) — filtered by a shape
    heuristic (must contain a digit, hyphen, or multiple internal capitals)
    that excludes italicized species/genus names (*Phaseolus*, *vulgaris*)
    and emphasized English words without needing an explicit denylist
  - KNOWN AMBIGUITY HANDLED: "Co-1" collides with "Cobalt-1" in chemistry/
    nutrient contexts. If "cobalt" appears within ~20 characters of a Co-N
    match, it's excluded.

INTEGRATION (hf_space/app.py, chat()'s local-mode branch): _verify_gene_mentions(answer)
  runs UNCONDITIONALLY after the LLM generates its answer — NOT gated by the
  query router's run_gene_validation flag (STEP 17). Reasoning: this check
  is free (regex + dict lookup, no LLM/API call) and already self-limits to
  whether the ANSWER mentions a gene at all. A query with zero genetics
  vocabulary can still produce an answer that names a gene (e.g. discussing
  disease resistance as a yield factor), and catching a hallucinated one
  there matters just as much — gating on the query-side flag would silently
  drop coverage for no cost savings. The router's flag is still logged as a
  routing/analytics signal, just not used to skip this check.

FOOTER FORMAT:
  "🧬 Gene/locus mentions:
   - Phvul.001G189200 — verified (NCBI 12345: <description>)
   - Co-1 — known classical genetics symbol (Anthracnose resistance locus);
     not independently cross-referenced in NCBI/UniProt
   - PvDREB2A — not found in NCBI Gene/UniProt for P. vulgaris; treat with caution"

BUILD: build_gene_index.py downloads gene_info.gz (~1.5GB, streams/filters
  without loading fully into memory) + UniProt's P. vulgaris subset, builds
  gene_id_map (gene_id → metadata) and symbol_map (lowercased symbol/synonym
  → [gene_ids]), pickles to vector_db/gene_index.pkl. Zero new pip
  dependencies (urllib.request is stdlib). See STEP 25 for the SLURM job —
  no GPU needed, but does need outbound HTTPS network access; the job script
  includes a login-node-download fallback path in its comments if compute
  nodes block that.

CHANGE 16: the gene-validation footer built from this module's functions is
  now ALSO wired into deploy/app.py (previously hf_space/app.py only) —
  full writeup lives in STEP 13's Change 16 section, since that's where the
  faithfulness check it was ported alongside is documented; nothing about
  gene_validator.py itself changed.

19. STEP 16 — STRUCTURED TRIAL-DATA LAYER  (Change 6, src/structured_data.py)
================================================================================

CONCEPT: The Bean Lab does not have a standardized trial-data spreadsheet —
  checked directly against the shared BeanLab filesystem (all lab members'
  readable directories, filename patterns for csv/xlsx/xls/db/sqlite, and
  yield/trial/variety/cultivar keywords) before concluding this, not assumed.
  Nothing turned up. This layer is the fallback: extract structured numeric
  trial data (yield, disease scores, agronomic traits) from the same 1,067
  papers' table chunks, using an LLM, into a real queryable SQLite database.

★ HONESTY BOUNDARY (stated directly in extract_structured_data.py's own
  docstring so it travels with the code, not just in this doc): every row in
  vector_db/trial_data.db is LLM-derived from noisy, whitespace-heuristic-
  detected table blobs (pdf_processor.py's table detection, STEP 3), NOT a
  real lab spreadsheet or a clean structured parse. It carries its own
  extraction-error and hallucination risk and does NOT have the same
  trustworthiness guarantee a real lab-maintained database would. Spot-check
  a sample against source PDFs before relying on it.

FILES:
  src/extract_structured_data.py — offline: scans processed_chunks.json,
    identifies candidates, calls Ollama to extract rows, writes to SQLite
  src/structured_data.py — runtime: read-only query interface against the
    SQLite database, copied identically to hf_space/

CANDIDATE DETECTION (is_extraction_candidate(), favors RECALL over precision
  — the opposite tradeoff from gene_validator's extraction, STEP 15 — since a
  missed candidate silently loses real data, while an over-included one just
  costs one wasted LLM call that returns an empty array):
  - Table-shaped chunks: mirrors pdf_processor.py's own is_table_row()
    heuristic (pipe chars or 3+ space gaps), since table chunks preserve
    their original per-line layout intact through chunking
  - OR: high digit density (>3%) + a trait keyword nearby (yield, kg/ha,
    t/ha, disease severity, days to maturity, seed weight, etc.) — catches
    numeric data given in prose ("cv. Rex yielded 2400 kg/ha at Elora in
    2019") that isn't formatted as a table at all

KNOWN CHUNKING GAP AND HOW IT'S WORKED AROUND: a table's caption — which
  usually states the location/year/study — is text, so pdf_processor.py's
  chunking (STEP 3) puts it in a DIFFERENT chunk than the table itself. For
  each candidate, extract_structured_data.py sends the target chunk PLUS its
  immediately-neighboring chunks (same source_file, adjacent chunk order) to
  the LLM as context, with explicit instruction to extract data only from
  the target passage but use the neighbors to resolve location/year/study
  identification.

EXTRACTION PROMPT RULES: only extract values explicitly stated (no
  inferring/averaging/guessing); a value with no associated cultivar name is
  dropped; "trait" is a short label (yield, disease_severity,
  days_to_maturity, seed_weight, plant_height, protein_content); "unit" is
  captured as written (kg/ha, t/ha, 1-9 scale, %, days); location/year may be
  null if genuinely not stated anywhere in the passages provided.

SQLITE SCHEMA (vector_db/trial_data.db, table trial_records):
  id, cultivar, location, year, trait, value, unit, source_doi, source_page,
  source_chunk_id, raw_context (first 2000 chars of the source chunk, for
  manual auditing). Indexed on cultivar, location, year, trait.

QUERY INTERFACE (structured_data.py):
  query_trial_data(cultivar=, location=, year=, year_range=, trait=, limit=200)
    — case-insensitive partial match (SQL LIKE) on string filters, since
    LLM-extracted spelling won't always exactly match a user's query. ALL
    filter values are bound as parameters (?), never string-formatted into
    SQL, regardless of input — verified with a real SQL-injection string
    against a real test database: 0 rows returned, table confirmed intact
    afterward.
  get_available_cultivars() / get_available_locations() / get_available_traits()
    — distinct values, used by query_router.py (STEP 17) to check whether a
    query's mentioned terms actually resolve to something in the database,
    rather than a hardcoded (and inevitably false-triggering) keyword list.
  format_trial_results(rows) — citation-style markdown formatter, mirroring
    prompts.py's format_references(); the query router / answer pipeline
    passes its output straight into build_messages()'s trial_data_block
    parameter (STEP 7) without prompts.py needing to know the row schema.

Lazy-loaded read-only connection, same candidate-path pattern as BM25 and
  gene index: vector_db/trial_data.db, /tmp/vector_db/trial_data.db, or
  $BEAN_TRIAL_DB — travels for free through the same HF Dataset repo once
  pushed there (STEP 11).

NOT BUILT in Change 6: the query router that decides WHEN to activate this
  vs. literature-only — that's Change 7 (STEP 17).

── CHANGE 14: PER-PAPER STRUCTURED METADATA INDEX (scripts/build_paper_

================================================================================
20. STEP 17 — QUERY ROUTER  (Change 7, src/query_router.py;
    unified with GraphRAG mode detection in Change 12; paper_metadata.db
    filtering wired in via Change 17)
================================================================================

CONCEPT: Before Change 7, every question took the same path: expand → hybrid
  retrieve → rerank → LLM. After Changes 5 and 6 there are three subsystems
  that need different handling: the vector database (literature), the
  structured trial data (STEP 16), and the gene validator (STEP 15, a
  post-generation check). The router decides which combination of these to
  activate per question — as independent FLAGS, not a single mutually-
  exclusive category (unlike a design that picks one bucket: genetics OR
  bean_data OR climate) — because a question like "What is the yield of navy
  beans with Co-1 resistance in Michigan trials?" is simultaneously a
  literature question, a structured-data question, and a genetics question,
  and needs all three active at once.

FILE: src/query_router.py, copied identically to hf_space/. Imported by
  qa_with_ollama.py (and therefore eval_qa.py, eval_ragas.py automatically)
  and hf_space/app.py — one shared module rather than copy-pasting routing
  logic into each surface, avoiding the same drift risk that already bit
  this project once (hf_space/retriever.py vs. src/retriever.py, ERROR 11).

DESIGN: rule-based only, no LLM classifier call. Unlike a GPT-4o-classifier-
  per-query design, this costs nothing extra on the 80%+ of questions that
  are plain literature queries. An LLM disambiguation fallback for
  "ambiguous cases" was considered but NOT implemented — "ambiguous" was
  never given a crisp trigger condition, and a query matching none of the
  rules already has a safe, well-defined default (use_literature stays True,
  the other two stay False). route()'s signature leaves room to add this
  later without changing callers.

RoutingDecision dataclass (richer than plain booleans, deliberately):
  mode ("local" or "global" — see CHANGE 12 below), use_literature (~always
  True), use_structured_data, run_gene_validation, PLUS the actual matched
  entities: detected_cultivars, detected_locations, detected_traits,
  detected_genes, detected_year, detected_year_range. Necessary, not just
  nice-to-have: query_trial_data(cultivar="Rex", location="Elora",
  year=2019) needs those actual values — a bare boolean flag would force
  re-parsing the query a second time downstream to recover the same
  information, wastefully and fragilely.

── CHANGE 12: UNIFYING THE TWO ROUTERS ──
  Before this change, two independent, uncoordinated systems decided things
  about the same incoming query: this module (rule-based, entity-aware,
  flag-based), and a completely separate standalone _is_global() in
  hf_space/app.py — a keyword-list check that ran BEFORE route() and gated
  the ENTIRE pipeline into "local" or "global" before route() ever saw the
  question. A query like "yield trends across all Michigan navy bean
  trials" is structurally both a structured-data question (this router
  should catch "yield," "Michigan," "navy") and a broad-synthesis question
  (STEP 19's global mode should catch "trends," "across all") — but the old
  structure made that impossible to express: _is_global() picked one path,
  and route() only ever ran, and only ever COULD run, inside the "local"
  branch _is_global() had already picked for it.

  Fix: _GLOBAL_SIGNALS and the keyword check that used to be hf_space/
  app.py's _is_global() now live in this module, and route() sets
  decision.mode as one more field on the SAME RoutingDecision it already
  returns, computed in the SAME pass as the other three flags.
  hf_space/app.py's chat() now calls route() exactly ONCE, at the top of
  the function, and branches on decision.mode — where it used to call a
  separate standalone function first, then call route() a second time,
  separately, only inside the branch already chosen. Net effect: one
  call site, one decision object, where there used to be two of each.

  SUPERSEDED BY CHANGE 13 (see STEP 19's Change 13 section): route() still
  computes decision.mode exactly as described above, but hf_space/app.py's
  chat() stopped reading it — Change 13 replaced keyword-based mode
  selection with a confidence-based one, decided AFTER local retrieval runs
  rather than from keywords before it. decision.mode is not removed (still
  computed, still correct, still available to any future consumer) — it's
  just not part of how mode gets chosen in the Space anymore. Left here,
  not deleted, so this section's history stays accurate rather than
  rewritten to look like Change 13 was the plan all along.

  Scope deliberately kept narrow: mode is still exactly one of "local" or
  "global" — never "both" — even though the Michigan/navy-bean example
  above clearly wants both structured-data lookup AND community synthesis
  running at once. Verified directly (not just claimed) that the
  UNDERLYING decision object no longer forces a choice between them: with
  synthetic structured-data vocabulary injected into the cache, route()
  returns mode="global" and use_structured_data=True on the SAME
  RoutingDecision for that exact query — structurally impossible before
  this change. What's still NOT done: hf_space/app.py's chat() still only
  ACTS on one mode — the "global" branch doesn't consume
  use_structured_data, and there's no concurrent local+global execution or
  answer-merging. That's real, separate work (new prompt assembly, new UI
  handling for two result sets, deciding how to present a combined answer)
  left for a later change, not silently papered over here — this change
  fixes the structural bug (two uncoordinated decision points) without
  also solving concurrent execution in the same commit.

  use_literature/use_structured_data/run_gene_validation are computed
  IDENTICALLY regardless of mode — route() doesn't special-case "global"
  queries when detecting genes or structured-data terms. Confirmed
  qa_with_ollama.py (and both eval scripts, which import route() through
  it) gain decision.mode "for free," the same way they gained
  use_structured_data/run_gene_validation in Change 7 originally — but
  this is inert for them today: GraphRAG artifacts (community_reports.json,
  community_embeddings.npy) are loaded ONLY in hf_space/app.py, confirmed
  by checking qa_with_ollama.py directly before making this change, not
  assumed. deploy/app.py has neither _is_global() nor route() at all,
  confirmed the same way — unaffected by this change either way.

  Backward compatibility: mode was added as a new dataclass field, not a
  signature change to any existing field — existing consumers reading
  use_literature/use_structured_data/run_gene_validation/detected_* are
  unaffected. Verified directly: RoutingDecision's constructor signature,
  route()'s return type, and qa_with_ollama.py's own syntax all still parse
  and import cleanly against the updated module.

  TESTED with synthetic queries covering each case: a pure local lookup
  ("What diseases affect common bean?"), a pure global/thematic question
  ("What are the major trends in bean breeding research over time?"), a
  gene-mention query in each mode (confirming run_gene_validation is
  independent of mode), and the flagship mixed-signal Michigan/navy-bean
  example (confirming mode and use_structured_data can now coexist on one
  decision object) — all matched expectation before this was wired into
  hf_space/app.py's chat().

DETECTION STRATEGY:
  - Gene mentions: reuse gene_validator.extract_gene_mentions() DIRECTLY —
    not reimplemented here, so the hardened patterns (including the
    Cobalt-1/Co-1 negative-context guard, STEP 15) can't drift out of sync
    between two copies. Plus a separate _GENETICS_KEYWORDS_RE for generic
    vocabulary (QTL, allele, marker, chromosome, locus, genotype, "gene
    expression") — a genuinely distinct concern from gene-NAME extraction,
    so no duplication risk.
  - Cultivar/location/trait: checked against the REAL current values in
    structured_data.get_available_cultivars/locations/traits(), cached once
    per process as frozensets — NOT a hardcoded keyword list. A hardcoded
    list would false-trigger constantly ("Black"/"Red" are both market
    classes and ordinary English words; "Elora" could appear in a paper's
    author affiliation rather than as a trial site). Checking against what's
    ACTUALLY in the database only fires when a term genuinely resolves to
    something, and stays correct automatically as trial data is added —
    nothing to maintain in parallel.
  - ONE DELIBERATE DEVIATION from pure per-token set membership: real
    cultivar names can be multi-word ("Black Turtle Soup") or hyphenated,
    and Change 6's trait labels use underscores ("days_to_maturity") that
    never appear in natural phrasing ("days to maturity"). Per-token hash
    lookup silently misses both. Matching is a word-boundary regex search
    per cached value instead (normalizing underscores to spaces first) —
    still frozenset-backed, still fast at the realistic scale of a lab's
    trial data (tens to low hundreds of distinct values), just not a literal
    O(1) hash lookup. Verified against both edge cases directly.
  - Year: a simple \b(19|20)\d{2}\b regex; multiple distinct years in one
    query become a year_range instead of a single year.

INTEGRATION AND ORDERING FIXES THIS REQUIRED (both in qa_with_ollama.py and
  hf_space/app.py):
  - Literature retrieval and structured-data lookup run CONCURRENTLY via
    ThreadPoolExecutor, not sequentially — they're independent of each
    other. In hf_space/app.py's chat(), which is a plain synchronous
    generator (not async def — worth being precise about this), threads are
    the right tool specifically because there's no async context to plug
    into.
  - strict_evidence (qa_with_ollama.py) and hf_space/app.py's out-of-scope
    gate both used to hard-stop purely on literature-retrieval confidence.
    Both now check for structured trial data FIRST — a narrow "yield of X
    in Y" question can have genuinely thin literature coverage but a real
    structured-data answer, and the old logic would have discarded it
    before this fix. CORRECTED (Change 16, was wrong here before): this
    does NOT include deploy/app.py's out-of-scope gate — confirmed directly
    by tracing its imports, structured_data.py was never imported there at
    all, so there was no structured-data path to check first. deploy/app.py
    still hard-stops on literature confidence alone for this specific gate,
    same as it always has; Change 16 didn't touch this (see STEP 19's
    Change 16 section for what it did and didn't port).
  - Gene validation runs unconditionally regardless of run_gene_validation
    (see STEP 15's integration note) — the flag is a signal, not a gate.
  - Raw-vs-expanded query handling required NO extra plumbing beyond what
    the router already does: since the router extracts specific matched
    STRINGS from the raw query (not the whole query text, expanded or not),
    and query_trial_data() is called with exactly those extracted strings,
    the raw/expanded separation the design asked for falls out of the
    router's own construction rather than needing separate handling.

TESTED END-TO-END with synthetic fixtures at every layer (router decision →
  structured_data query → prompts.build_messages() prompt assembly),
  including the flagship example: "What was the yield of Rex in Elora in
  2019?" correctly detects cultivar=Rex, location=Elora, trait=yield,
  year=2019, and the assembled prompt places the resulting TRIAL DATA
  section before RETRIEVED SOURCES exactly as designed.

── CHANGE 17: WIRING paper_metadata.db (CHANGE 14) INTO ROUTING ──
  CONCEPT: Change 14 built the per-paper (DOI/year/species/methodology)
  SQLite index and its query interface, then deliberately stopped — no
  detection logic existed anywhere to notice a question wanted it, and the
  built vector_db/paper_metadata.db was never uploaded. Both closed here,
  in direct response to being asked "why isn't this wired in" after

  DETECTION reuses the SAME two mechanisms this section's router already

21. STEP 18 — CONVERSATION MEMORY  (Change 8, hf_space/app.py + prompts.py)
================================================================================

CONCEPT: Before Change 8, every question was answered independently — a
  follow-up like "Which of those are found in navy bean cultivars?" had no
  antecedent for "those" to resolve against. Change 8 adds a per-session
  short-term memory: the last 3 question/answer pairs, replayed to the LLM
  as real conversation turns, plus a small retrieval-side fix so follow-up
  questions actually find the right chunks in the first place.

FILES: hf_space/app.py (session store, wiring), hf_space/prompts.py +
  src/prompts.py (build_messages_with_history(), kept in sync per the usual
  convention even though only the Space currently calls it — batch/HPCC
  runs, STEP 8, don't have a multi-turn "session" concept to hang memory on,
  so this is scoped to the Space only, same as Changes 3 and 5).

★ A DISCOVERY THAT CHANGED THE SCOPE OF THIS CHANGE: hf_space/app.py already
  had a partial, ad hoc attempt at conversation memory before this — it
  built a "context_query" by blindly concatenating the last 4 rendered
  Gradio chat messages (200 chars each) onto every retrieval query,
  regardless of whether the current question needed it, and separately
  spliced the last 6 rendered messages into the LLM's message list as fake
  prior turns. Two real problems were found in it, not assumed:
  1. It always diluted the retrieval query with recent conversation text,
     even for fully self-contained questions — this hurts retrieval
     precision on the majority of questions that AREN'T follow-ups.
  2. Far more serious: it fed a multi-message array into call_llm(), but
     _call_gemini() — the Tier 1 handler, used for the large majority of
     answers thanks to Gemini's generous free quota — collapsed the ENTIRE
     messages list down to just the FIRST system message and the FIRST user
     message via `next(...)`. Once a second turn existed, that first "user"
     message was an OLDER question, not the current one — meaning the
     current question and its freshly retrieved RETRIEVED SOURCES block
     were silently dropped from what Gemini actually saw. Verified directly
     (not assumed) by reproducing the exact string Gemini would have
     received before and after the fix — see ERROR 16.
  Because of finding #2, implementing Change 8's spec correctly required
  fixing _call_gemini() first — otherwise the new, more deliberate history
  feature would have inherited the exact same silent-drop bug.

HOW IT WORKS NOW:

  1. SESSION STORE (hf_space/app.py): a server-side dict, `_conversations`,
     keyed by `request.session_hash` (the same identifier already used by
     the rate limiter) — NOT the Gradio `history` UI list. This is a
     deliberate change from the old ad hoc approach: `history` is display
     state — it contains step-status placeholders ("Retrieving relevant
     passages...") and the fully footer-laden final answer (faithfulness
     warning + gene footer + reference list) — none of which are things a
     future turn should be asked to reason about as if they were real
     conversation content.
       _get_history(session)             → last ≤3 (question, answer) tuples,
                                            or [] if the session has no entry
                                            or its last activity was more
                                            than CONVERSATION_TTL ago
       _append_history(session, q, a)     → appends the CLEAN answer (before
                                            any footer/references are added),
                                            truncated to 1500 chars, trims to
                                            the last CONVERSATION_TURNS (3)
       CONVERSATION_TTL = 30 * 60 seconds; CONVERSATION_TURNS = 3
     A daemon thread (_sweep_conversations, same pattern as the existing
     _logger_thread) purges sessions whose last activity exceeds the TTL
     every 5 minutes, so abandoned sessions don't grow _conversations
     unboundedly — well within the Space's 16GB RAM limit at any realistic
     concurrent-user count.

  2. RETRIEVAL-SIDE COREFERENCE (hf_space/app.py, _needs_context() /
     _augment_query_with_history()): rather than always prepending prior
     text (the old approach's flaw), the previous question is prepended to
     the CURRENT query ONLY when the current message looks like it can't
     stand alone — contains a pronoun (it/its/this/that/these/those/they/
     them/their/itself) or is at most 6 words. This is intentionally a
     cheap heuristic (regex + word count), not an LLM call: a false
     positive only costs a little extra (harmless) context on the
     embedding; a false negative just means that one query behaves as it
     did before Change 8. Only the immediately preceding question is
     prepended — not the answer, and not older turns — since the antecedent
     for a pronoun is almost always in the question just asked. This
     augmented query is used for retrieval only; the router (STEP 17) still
     runs on the raw, un-augmented message, matching the router's own
     already-established principle of routing off raw text.

  3. LLM-SIDE HISTORY REPLAY (build_messages_with_history(), prompts.py,
     both copies): builds `[system] + [user, assistant] * up to 3 prior
     turns + [current fully-formatted user turn]`. The current turn's
     message (RETRIEVED SOURCES + TRIAL DATA + question) is built by calling
     the existing build_messages() and taking just its last (user) entry —
     no duplicated context-assembly logic. Prior turns replay only their
     plain question/answer text, NOT that turn's retrieved sources or trial
     data — this bounds prompt growth to roughly 3x a question+answer pair
     rather than 3x a full context dump, and means the model treats earlier
     answers as established conclusions rather than re-deriving them from
     stale evidence each turn (the CURRENT turn's retrieval is what supplies
     fresh evidence).

  4. GEMINI MULTI-TURN FIX (_call_gemini(), hf_space/app.py): now converts
     the ENTIRE messages list into Gemini's actual multi-turn shape — all
     system-role content joins into a top-level `systemInstruction`, and
     every remaining message becomes one entry in `contents`, with role
     "user" kept as "user" and "assistant" mapped to Gemini's "model" role.
     This is what makes step 3 actually reach the model correctly instead
     of being silently truncated to the first user message — see ERROR 16.

WHAT WAS DELIBERATELY NOT DONE:
  - No LLM-based coreference resolution — the cheap heuristic in step 2 was
    judged sufficient for the stated goal ("simple coreference resolution");
    an LLM call per query would cost real quota for a problem the regex
    already handles for the common cases described in the request (pronouns,
    short follow-ups).
  - Not wired into qa_with_ollama.py / eval_qa.py / eval_ragas.py / deploy/
    app.py — batch evaluation runs ask each benchmark question independently
    by design (STEP 9's benchmark has no notion of question sequence or
    session), and deploy/app.py has not received any of the Space-only
    features added since Change 3 (faithfulness, gene footer, structured
    data, router) — conversation memory follows the same established scope
    boundary.
  - _call_groq() / _call_openrouter() / _call_together() needed NO changes —
    they already forward the full `messages` array to standard OpenAI-
    compatible chat endpoints, which have supported multi-turn message
    arrays all along. Only Gemini's REST API (used directly via requests.post(),
    not an SDK — see the LLM waterfall section under STEP 10) has its own,
    different multi-turn shape, which is what _call_gemini() had never
    accounted for.

22. STEP 19 — GRAPHRAG GLOBAL QUERY MODE  (Change 9, scripts/, hf_space/app.py;
    + Change 13, escalating router; + Change 15, bounded gap-check loop —
    both live here despite the section title, since this is where chat()'s
    "what to do about a weak local retrieval" decision chain already lives)

CONCEPT: Not every question is about one specific fact findable in a handful
  of chunks. "What are the major trends in bean breeding research over the
  last 30 years?" needs a synthesis ACROSS the whole corpus, not just the
  top-6 most similar passages — no single paper's chunks answer it. GraphRAG
  (Microsoft's approach) addresses this by first clustering the corpus into
  topic "communities," summarizing each community once (offline, expensive),
  and at query time retrieving/synthesizing from those community summaries
  instead of raw chunks.

  UPDATED IN CHANGE 12, THEN SUPERSEDED BY CHANGE 13: Change 12 folded a
  previously-standalone keyword check (_is_global()) into query_router.py's
  route() as one more field (decision.mode) on the shared RoutingDecision
  object — one router, one call site, instead of two uncoordinated ones,
  but mode was still decided from keywords alone, before any retrieval. See
  STEP 17's CHANGE 12 section for that history. Change 13 (below) replaces
  keyword-based mode selection entirely with a confidence-based one —
  decision.mode is still computed by route() but is NO LONGER READ by
  hf_space/app.py's chat() as of Change 13; _GLOBAL_SIGNALS itself is
  untouched in query_router.py, just unconsulted for this purpose now.
    mode decision, as of Change 13 (see CHANGE 13 section below):
      confidence-based, computed AFTER local retrieval already ran, not from
      keywords before it.
    "local"  → the normal per-question retrieval pipeline (STEP 6/12 + router)
    "global" → GraphRAG: embed the question, find the top-5 most similar
               community reports, feed their summaries to the LLM, and also
               render a highlighted subgraph of the papers in those
               communities (via pyvis) so the answer comes with a visual
               map of which paper cluster it's drawn from

── CHANGE 13: ESCALATING ROUTER (hf_space/app.py's chat(), not
  query_router.py — GraphRAG is Space-only, so this whole mechanism lives
  where GraphRAG already lives) ──
  CONCEPT: a fixed keyword list can't know whether a question is actually
  well-covered locally — it can only guess from phrasing. "What are bean
  yield trends over time" contains "trends" and goes global whether or not
  the corpus happens to have a great specific answer; "How do bean cultivars
  compare for rust resistance" contains "compare" and goes global even if
  it's really a narrow, well-covered local question. Change 13 replaces the
  guess with a measurement: run the (cheap — no LLM call) local retrieval
  FIRST, for every question, and decide mode from what assess_confidence()
  (Change 2, src/retriever.py) actually found.

  DECISION, finalized in writing (hf_space/app.py, as a spec comment
  directly above chat(), before the implementation was written — not
  re-derived from a chat log after the fact) BEFORE coding, per this
  project's established discipline for decisions that would otherwise drift
  the way NO_MATCH_THRESHOLD/THRESHOLD_UNSUPPORTED already have:
    escalate = global_available AND trial_rows is empty AND
               confidence != "SUPPORTED" AND NOT none_distance_artifact
  Five sub-decisions behind that one line:
    1. TRIGGER is the confidence LABEL, not UNSUPPORTED alone. Checked
       against 11 questions independently verified (Change 11) to have real
       corpus support and 9 verified to have none: INFERRED never fired
       across 23 real test queries, and UNSUPPORTED alone only caught 1 of
       9 confirmed-thin questions — escalating only on UNSUPPORTED would
       have missed most of the real problem cases. "!= SUPPORTED" (i.e.
       PARTIALLY_SUPPORTED, INFERRED, or UNSUPPORTED all escalate) is what
       the real distribution actually supports.
    2. decision.mode (the OLD keyword signal) is explicitly NOT part of the
       trigger — confirmed, not assumed, after catching an internal
       contradiction: "confidence low OR keyword suggests breadth" (a plain
       OR) would mean a keyword-matched query ALWAYS escalates even when
       local retrieval comes back SUPPORTED, directly breaking the design
       goal of avoiding expensive graph search on a query that's secretly
       answerable locally despite containing a trigger word. Confidence
       alone already satisfies both goals: a genuinely broad question lands
       non-SUPPORTED without needing a keyword, and a keyword-matched but
       well-covered question lands SUPPORTED and correctly stays local.
    3. GUARD — a None distance (chunks[0] came from BM25 only, no dense
       embedding score) is NOT a measured low-confidence signal, and
       assess_confidence()'s _dist() defaults it to 1.0 — the worst case,
       mathematically guaranteed to produce UNSUPPORTED specifically (1.0
       fails even THRESHOLD_INFERRED, so this can only ever manifest as
       UNSUPPORTED, never PARTIALLY_SUPPORTED/INFERRED). Not hypothetical:
       3 of the same 23 test queries (13%) had a None top distance, and one
       was a CONFIRMED well-covered question (nitrogen fixation rates) that
       landed UNSUPPORTED purely from this artifact. Guard: UNSUPPORTED +
       None top distance does NOT escalate — mirrors hf_space/app.py's
       _out_of_scope(), which already refuses to treat the identical signal
       as evidence of no match, for the identical reason.
    4. Non-empty trial_rows (structured trial data, Change 6/7) BLOCKS
       escalation — if structured data can still answer the question, that's
       a real local answer, not a reason to discard it for global synthesis.
    5. SCOPE is full replacement, no merging: escalation means ONLY the
       global-mode answer gets generated — the check happens before the
       local LLM call, so nothing is generated only to be discarded. No
       concurrent local+global execution or answer-combining — deliberately
       deferred, same "both"-mode boundary Change 12 already drew.

  STRUCTURAL CHANGE: local retrieval (+ concurrent structured-data lookup,
  + out-of-scope retry) now runs UNCONDITIONALLY first, for every
  non-greeting question, rather than being gated behind a pre-decided mode.
  mode starts "local" and is set to "global" only via the escalation check
  above — there is no other path to mode=="global" in chat() as of this
  change. One incidental resilience improvement this reordering yields for
  free: if `retriever` itself is unavailable, that's now treated as maximal
  low confidence (chunks=[], confidence defaults to UNSUPPORTED) rather than
  an immediate hard failure — escalates to global if that's viable, only
  fails outright if global isn't viable either.

  VERIFIED before shipping, in two layers:
    1. A full decision-matrix test (11 cases) against the exact boolean
       expression copied verbatim from the file — every combination of
       trigger label, the None-distance guard, trial_rows, and global
       availability, including the retriever-unavailable resilience case.
    2. The SAME 23 real queries used to originally diagnose this (11
       confirmed-covered, 9 confirmed-not-covered, 3 out-of-scope — real
       vector_db, real retriever, no mocking) run back through the shipped
       should_escalate logic: confirmed-covered questions stay local 82% of
       the time (2/11 escalate — an accepted, bounded false-positive cost);
       confirmed-not-covered questions escalate 67% of the time (6/9) — vs.
       only 11% (1/9) under the rejected "escalate on UNSUPPORTED alone"
       design. The nitrogen-fixation None-distance case specifically stayed
       local in this real-data run too, confirmed via the guard catching it
       (not coincidence — the other Group-A escalation was a genuine
       PARTIALLY_SUPPORTED case, not the None-distance one).

── CHANGE 15: BOUNDED GAP-CHECK LOOP (Self-RAG, hf_space/app.py — local
  retrieval only, does not touch this section's GraphRAG machinery at all)
  ──
  CONCEPT: Self-RAG (STEP 13's faithfulness check, "Self-RAG lite") checks
  an answer AFTER generation. Change 15 adds the same idea BEFORE
  generation: once local retrieval settles, ask a cheap Gemini call "is
  this context actually enough to answer the question, and if not, what
  search query would find something better" — and if not, reformulate and
  retrieve again, capped at 2 iterations.

  NOT a second, competing "is this good enough" mechanism sitting beside
  Change 13's escalation decision just above — that would be exactly the
  uncoordinated-second-decision-point problem Change 12 was built to
  eliminate in the first place. This is a refinement layer UNDERNEATH
  Change 13: it may improve (chunks, confidence) before should_escalate
  ever reads them, but should_escalate itself is completely unchanged —
  still reads whatever (chunks, confidence, trial_rows) exist when it runs,
  regardless of whether this loop touched them first.

  DECISION, finalized in writing (hf_space/app.py, spec comment directly
  above chat(), before the implementation) same discipline as Change 13:
    1. TRIGGER — same base condition as Change 13's escalation
       (confidence != "SUPPORTED"), gated on not trial_rows (identical
       reasoning: structured data already answering the question means no
       need to spend an LLM call improving literature retrieval) — but
       DELIBERATELY WITHOUT Change 13's none_distance_artifact guard. That
       guard exists because a raw distance value can't tell whether a
       None-distance (BM25-only) top chunk is good evidence or not; this
       loop's classifier is a DIRECT, qualitative read of the actual chunk
       text — exactly the higher-fidelity signal the distance guard can't
       provide. Running the gap-check specifically on that ambiguous case,
       instead of skipping it, is the point: without this change it's a
       dead end Change 13 just accepts; with it, that case gets a real
       chance to improve via reformulation before Change 13 ever decides
       anything about it.
    2. ITERATIONS — "capped at 2" means up to 2 reformulate-AND-retry
       cycles (up to 3 total retrieval calls per question, counting the
       free initial one Change 13 already made unconditional). Each
       iteration is ONE combined Gemini call — sufficiency judgment AND a
       suggested better query in the SAME JSON response, not two
       round-trips — followed by, only if insufficient, one retrieval
       call. Exits early on sufficient=True, on confidence reaching
       SUPPORTED mid-loop (no point asking again), or on any Gemini
       failure (point 4).
    3. WHAT'S PASSED TO THE CLASSIFIER: the ORIGINAL question (`message` —
       never the reformulated search string, so the judgment is always
       against what was actually asked), the search query that actually
       produced the current chunks, and build_context(chunks) — the SAME
       formatting helper Change 9a's _verify_faithfulness() already uses,
       not reimplemented.
    4. SOFT-FAIL, identical philosophy to _verify_faithfulness(): missing
       API key, a failed request, or unparseable JSON all default to
       (sufficient=True, reformulated_query=None) — stop looping, proceed
       with whatever (chunks, confidence) already exist. A broken
       sufficiency check can never make an answer worse than the
       pre-Change-15 baseline, only occasionally fail to make it better.
    5. SCOPE — local retrieval only. Reformulating for ~21,876 individual
       chunks has much more to gain than reformulating for the coarse,
       fixed set of ~5 community reports Change 13 already reasoned about;
       this loop lives entirely inside chat()'s `if retriever is not
       None:` block, structurally unable to touch the global branch.
    6. COST, stated plainly rather than hidden behind "cheap": the trigger
       condition (confidence != SUPPORTED) fired on 18% of confirmed-
       covered and 89% of confirmed-thin questions in Change 13's own
       calibration data — this loop can add up to 2 extra Gemini
       round-trips and 2 extra retrieval calls, before generation even
       starts, on top of that share of real traffic. A new status message
       (_STEP_REFINING = "Refining search...") is shown while it runs, so
       the added latency reads as visible progress, matching every other
       multi-second step in chat().

  IMPLEMENTATION: _check_context_sufficiency(question, search_query,
  context) — one Gemini call, same try/except/regex-extract/json.loads
  soft-fail chain as _verify_faithfulness(), returns
  (sufficient: bool, reformulated_query: Optional[str]).
  _gap_check_retrieve(message, search_query, chunks, confidence,
  retriever_obj, max_iterations=2) — the loop itself, a plain function
  (not a generator — chat() yields _STEP_REFINING once before calling it,
  matching how _search_communities()/_render_graph() are already called:
  status yields happen in chat() around a call, never inside a nested
  generator). Wired in between the existing free out-of-scope retry
  (context_query → message fallback, unchanged) and Change 13's
  should_escalate computation — a new `search_query` variable tracks
  whichever query text actually produced the current chunks (starts as
  context_query, becomes message after the free retry, becomes each gap-
  check iteration's suggested reformulation after that), kept entirely
  separate from `message`, which stays the true original question
  throughout for generation/citation/history.

  VERIFIED before shipping: an 8-case test against
  _check_context_sufficiency() and _gap_check_retrieve() copied VERBATIM
  from hf_space/app.py (confirmed statement-for-statement via Python's ast
  module, not eyeballed) with _call_gemini and retriever.retrieve mocked —
  iteration capping at 2, early-exit on sufficient=True, early-exit when a

  All four output files (community_reports.parquet is NOT uploaded — only

RUNTIME LOADING (hf_space/app.py startup, current — see ERROR 17 for what
  this replaced):

24. KEY ERRORS ENCOUNTERED AND HOW THEY WERE FIXED
================================================================================

ERROR 1: transformers incompatible with huggingface-hub
  Symptom: ImportError when importing sentence_transformers on HPCC
  Cause: sentence-transformers required transformers<4.46 which required
         huggingface-hub<0.24, but we needed huggingface-hub>=0.24 for
         snapshot_download to work correctly.
  Fix: conda run -n bean_llm pip install "transformers>=4.46.0"
       (newer transformers is compatible with any huggingface-hub version)

ERROR 2: HTTP 402 Payment Required from LLM API
  Symptom: ⚠️ LLM error: 402 Client Error: Payment Required
  Cause: HuggingFace Spaces sets OPENAI_BASE_URL environment variable to their
         paid inference router. The Groq SDK (and OpenAI SDK) both read this
         variable and redirect all API calls to HF's router, which requires payment.
  Fix: Stop using SDKs. Use requests.post() with hardcoded API URLs:
         requests.post("https://api.groq.com/openai/v1/chat/completions", ...)
       Raw HTTP calls ignore environment variables entirely.

ERROR 3: HTTP 413 Request Too Large from Groq
  Symptom: Groq returns 413 Request Entity Too Large
  Cause: Groq's free tier has a 6000 tokens/minute limit. Our initial config
         retrieved TOP_K=10 chunks at 512 tokens each = 5120 tokens of context
         plus the question and system prompt often exceeded 6000 total.
  Fix: Reduced TOP_K from 10 to 6. With TOP_K=6, total context ~3000 tokens
       → well within limit.

ERROR 4: Gemini API 404 with %0A in URL
  Symptom: ⚠️ Gemini error: 404 Client Error: Not Found
           URL contained %0A (URL-encoded newline)
  Cause: HuggingFace Spaces injects a trailing newline (\n) into secret values.
         The API key was "AIzaSy...xyz\n". When embedded in the URL for Gemini's
         REST API (?key=AIzaSy...xyz%0A), the URL becomes invalid.
  Fix: Added .strip() to all secret reads:
         GEMINI_API_KEY = os.environ.get("Googlegeminiapi", "").strip()

ERROR 5: Space stuck in "Building" for 20+ hours
  Symptom: HuggingFace Space shows "Building" status with no progress
  Cause: vector_db/ (875 MB) was stored in the Space's own git repo via Git LFS.
         Every restart triggered git lfs pull which re-downloaded everything as
         part of the Docker build. The build timed out before completing.
  Fix:
    1. git rm -r --cached vector_db/  (stop tracking in Space repo)
    2. Pushed vector_db to a separate HF Dataset repo
    3. Added snapshot_download() to app.py startup code
    4. The Space now builds in ~2 minutes and downloads vector_db at runtime

ERROR 6: Space health check hanging (SSR mode)
  Symptom: App prints "Running on local URL: http://0.0.0.0:7860" in logs
           but Space stays in "Building" or "Restarting" state indefinitely
  Cause: Gradio 6.10 has Server-Side Rendering (SSR) enabled by default.
         SSR requires the app to handle an initial render request before HF's
         health check gets a 200 OK response. The SSR render was hanging.
  Fix: demo.launch(ssr_mode=False)

ERROR 7: Gradio UserWarning about theme/css in gr.Blocks

ERROR 14: Change 2's hybrid retrieval surfaced multiple None-distance bugs
  Symptom: Would have appeared as TypeError: '>' not supported between

ERROR 16: _call_gemini() silently dropped the current turn once conversation
          history existed (found while implementing Change 8)
  Symptom: Not observed as a live crash report — found via code review of
           hf_space/app.py's pre-existing (pre-Change-8) ad hoc conversation-
           history logic, then confirmed by reproducing the exact string
           Gemini would have received, both before and after the fix, in a
           synthetic test with no network calls.
  Cause: _call_gemini(messages) built its request as
         `sys_ = next(m["content"] for m in messages if m["role"]=="system")`
         and `usr_ = next(m["content"] for m in messages if m["role"]=="user")`
         — `next()` returns the FIRST match only. As long as `messages` held
         exactly one system + one user message (true for every call before
         Change 8's history feature), this was harmless. The moment a
         messages list contains multiple user/assistant turns (a
         prerequisite for any conversation-memory feature, old or new), this
         silently picks the OLDEST user message in the array as "usr_" and
         ignores every later one — including the current turn's actual
         question and its freshly retrieved RETRIEVED SOURCES/TRIAL DATA
         block, which live in the LAST user message, not the first. Gemini
         is Tier 1 in the LLM waterfall (STEP 10) and handles the large
         majority of answers given its free-tier quota, so this would have
         been the dominant behavior, not an edge case.
  Fix: Rewrote _call_gemini() to convert the full messages list into
       Gemini's actual multi-turn request shape: every "system" message's
       content joins into one top-level `systemInstruction`, and every
       remaining message becomes an entry in `contents`, mapping role
       "assistant" → Gemini's "model" (Gemini's own name for that role) and
       leaving "user" as "user". Verified with a synthetic messages list
       built from build_messages_with_history() (STEP 18): confirmed the
       new payload's last `contents` entry contains the current question and
       "RETRIEVED SOURCES", and confirmed the OLD code path's flattened
       string did NOT contain either — reproducing the bug and the fix side
       by side rather than reasoning about it in the abstract.
  Note: _call_groq(), _call_openrouter(), and _call_together() were NOT
       affected — they forward `messages` as-is to standard OpenAI-
       compatible endpoints, which already handle multi-turn arrays
       correctly. Only Gemini's REST API (called directly via requests.post(),
       not an SDK) has a different multi-turn shape that this codebase had
       never previously needed to produce.

ERROR 20: Chat input textbox unusable — clicking it produced no cursor, no
          typed text ever registered (present since commit 74b6afd, only
          root-caused Aug 5, 2026)
  Symptom: clicking inside the message box did nothing — no visible cursor,
           no character ever appeared while typing. Follow-up-question
           chips (which set the textarea's value via JS) worked fine,
           which is what made this genuinely confusing to diagnose from
           behavior alone.
  Cause: confirmed with a real headless-browser test (Playwright), not
         assumed — `#msg-box label { display: none !important; }` had been
         hiding Gradio 6.10's structural wrapper around the input
         (`label > input-container > textarea`), not a caption label as
         originally assumed when that rule was written. Hiding the
         wrapper collapsed the real `<textarea>` inside it to 0x0 —
         invisible AND unfocusable — while Gradio's own separate default
         styling on the #msg-box wrapper div kept rendering a normal-
         looking bordered box with nothing interactive inside it. The
         follow-up chips still worked because
         `document.querySelector('textarea').value = ...` sets a DOM
         property directly, which doesn't care whether the element is
         visible.
  Fix: removed the CSS rule entirely. `show_label=False` was already
       passed in Python for this component (STEP 7/msg Textbox
       definition) — the correct, Gradio-native way to suppress the
       caption, making the CSS override both wrong and unnecessary.
       Verified locally before pushing: extracted the real CSS into a
       minimal repro gr.Blocks app (no model/DB loading) and used
       Playwright to confirm the textarea now has real geometry, receives
       focus on click, and actually accepts typed input — then re-verified
       the same way against the live Space after deploying.

ERROR 21: Four undocumented Gradio 6.10 wiring quirks, found building the
          chat-history sidebar (Change 10 / STEP 20, Aug 6-7, 2026)
  Context: after ERROR 20 was caused by a blind CSS push, all further UI
    work this session was built and verified against a local headless-
    browser (Playwright) repro BEFORE touching the live Space. Building
    the sidebar surfaced four separate, real Gradio 6.10 behaviors along
    the way, none of which are documented anywhere in Gradio's own docs
    and each of which silently fails with no error in the server log,
    browser console, or SSE response — found only by isolating each down
    to a minimal reproducible Blocks app.
  (a) fn=None + js=-only output updates silently fail once a second
      gr.Textbox exists anywhere on the page. Gradio's js= parameter has
      two real modes: fn=None+js= computes and sets outputs purely
      client-side (no server round-trip); fn=<real function>+js= uses JS
      only to transform inputs before a real Python call. Mode 1 works
      fine with exactly one Textbox on the page and silently does nothing
      with two or more — confirmed via bisection down to a ~15-line repro,
      confirmed NOT a timing/race issue (polled 8+ seconds), confirmed the
      identical JS logic works when run directly via page.evaluate().
      Fix used everywhere in this feature: always a real (even if
      trivial) fn=, e.g. hf_space/app.py's `_identity()`; js= only
      transforms inputs, never computes outputs on its own.
  (b) gr.Textbox(visible=False) removes the element from the DOM
      entirely (confirmed: document.querySelector returns null) — not
      the same as CSS display:none on a wrapper. The sidebar needs two
      JS-writable-but-visually-hidden carrier textboxes (session_trigger,
      history_json); both use visible=True + CSS
      `position:absolute; left:-9999px; ...` instead. display:none on an
      ANCESTOR was already known to be destructive from ERROR 20 (collapses
      real interactive descendants to 0x0) — this is the same lesson
      applied to Gradio's own visible=False prop, not just hand-written
      CSS.
  (c) A synthetic `new Event('input')` dispatched via
      element.dispatchEvent(...) only reaches Gradio's Python-side handler
      through .change(), NOT .input() — confirmed directly by testing
      both. Every JS-driven trigger textbox in this feature is wired via
      .change().
  (d) Reading a gr.Chatbot's value via inputs=[chatbot] in a .then() step
      run immediately after that SAME chatbot was just updated by the
      preceding step silently fails — the .then() call comes back with a
      generic Gradio "Error" status and no detail anywhere (server log,
      browser console, or SSE response). Confirmed independent of js= and
      of what's done with the value, via a minimal isolated repro. Also
      confirmed: reading a Chatbot's value through js= returns a
      different, richer internal shape ({content:[{text,type}]}) than the
      plain {content:"string"} shape Python-side code builds it with, and
      trying to SET a Chatbot's value from a js= return using either shape
      fails (one silently, one with "messages.flatMap is not a function")
      — never set gr.Chatbot's value directly from js=; always route
      through a real Python function.
      Fix: chat_with_session_save() (hf_space/app.py) wraps the untouched
      chat() and yields history JSON-stringified as a 4th output directly
      from the SAME event that updates chatbot, so nothing ever needs to
      re-read chatbot's value in a later chained step. See STEP 20 above
      for how this is wired.
  Net effect: none of these four are guessable from Gradio's documentation
    or from a stack trace — each was found only by building a disposable,
    minimal reproduction and driving it with a real headless browser. This
    is now the standard approach for any further Gradio UI work on this
    project (verify locally with Playwright before pushing), not a one-off.

CONCEPT: What is SLURM?
  SLURM is the job scheduler on HPCC. Instead of running a script directly
  (which would use the login node's weak CPU), you submit it as a "job" and
  SLURM assigns it to a compute node with the resources you requested.

--- jobs/process_pdfs.sb ---
  Resources: 1 task, 8 CPUs, 32GB RAM, 4 hours, no GPU
  Purpose: Run src/pdf_processor.py on all PDFs
  Output: data/processed_chunks.json (~21,876 chunks)

--- jobs/generate_embeddings.sb ---
  Resources: 1 task, 4 CPUs, 32GB RAM, 2 hours, 1 GPU (V100)
  Purpose: Run src/generate_embeddings.py (BAAI/bge-large-en-v1.5, batch_size=16)
  Output: data/embeddings.npy, data/embeddings_metadata.json
  ⚠ As of August 5, 2026 this activates /mnt/home/kodumuru/.conda/envs/ptgpu,
    NOT bean_llm — see ERROR 19. Successfully re-run that day: job 14748450,
    639s on a V100, confirmed output shape (21876, 1024).

--- jobs/build_vector_store.sb ---
  Resources: 1 task, 4 CPUs, 16GB RAM, 1 hour, no GPU
  Purpose: Run src/build_vector_store.py — ChromaDB AND the BM25 index
           (Change 2 folded BM25 building into this same job/script)
  Output: vector_db/ (chroma.sqlite3, *.bin, bm25_index.pkl, database_statistics.json)
  ⚠ STILL points at the broken bean_llm env as of this writing (see ERROR
    19/STATUS note at top of file) — needs the identical ptgpu switch
    generate_embeddings.sb already got, or it will fail the same way.

--- jobs/build_graphrag.sb ---  (Change 9, NEW)
  Resources: 1 task, 8 CPUs, 32GB RAM, up to 4 days, 1 GPU (V100),
             partition general-long-gpu
  Purpose: Runs the GraphRAG indexing pipeline fully locally via Ollama —
           starts an Ollama server on the allocated GPU, pulls
           nomic-embed-text if not cached, runs graphrag.index using
           llama3.1:8b for entity/relationship extraction and
           nomic-embed-text for embeddings. No API keys, no rate limits,
           no cost. Produces graphrag_workspace/output/*.parquet.
  Long time limit (4 days) reflects that LLM-driven entity extraction over
  the full corpus is genuinely slow — cache in graphrag_workspace/cache/ is
  safe to resume from if the job gets killed partway.
  Downstream steps (not SLURM jobs — see STEP 19): after this completes,
  run scripts/export_graphrag_summaries.py, scripts/build_paper_graph.py,
  and scripts/embed_community_reports.py in that order (the last needs a
  GPU for the sentence-transformers encode step; run it interactively on a
  dev node rather than via sbatch — it's a one-off, fast job, not worth a
  separate job script for).

--- jobs/build_gene_index.sb ---  (Change 5, NEW)
  Resources: 1 task, 2 CPUs, 8GB RAM, 1 hour, no GPU
  Purpose: Run src/build_gene_index.py — downloads NCBI gene_info.gz +
           UniProt's P. vulgaris subset, builds vector_db/gene_index.pkl
  NEEDS: outbound HTTPS network access to ftp.ncbi.nlm.nih.gov and
         rest.uniprot.org. If compute nodes block this, the job script's
         comments describe downloading gene_info.gz on a login node first
         and passing it via --gene-info-path.

--- jobs/extract_structured_data.sb ---  (Change 6, NEW)
  Resources: 1 task, 8 CPUs, 32GB RAM, 8 hours, 1 GPU (V100) + Ollama
  Purpose: Run src/extract_structured_data.py — LLM-extracts trial data from
           candidate chunks into vector_db/trial_data.db
  Includes a --dry-run candidate-count check before committing GPU time to
  the full extraction pass; if the count is too large for the time budget,
  cancel and re-submit with --limit or split by year_range.

--- jobs/run_ollama_qa.sb ---
  Resources: 1 task, 8 CPUs, 32GB RAM, 4 hours, 1 GPU (V100) + Ollama
  Purpose: Run src/qa_with_ollama.py — batch QA against a question list.
           As of Change 7, automatically routes each question (literature /
           structured data / gene validation) with no flags needed; the old
           --hybrid/--bm25-index/--trace-file flags were removed in Change 2
           since hybrid retrieval is now automatic. --strict-evidence still
           works as before.

--- jobs/run_ragas_eval.sb ---  (Change 4, NEW)
  Resources: 1 task, 8 CPUs, 32GB RAM, 4 hours, 1 GPU (V100) + Ollama
  Purpose: Run src/eval_ragas.py against all 75 benchmark questions, judged
           by Gemini.
  NEEDS: Googlegeminiapi or GEMINI_API_KEY exported in your shell BEFORE
         calling sbatch (the job checks for this and exits early if unset).
